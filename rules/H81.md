Свод целиком — `DEPLOY_REQUIREMENTS.md`; оглавление правил — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H81. Вход противоречил промпту, и побеждал вход

**Замер 26.08.2026.** Готовый промпт запрещал: «не проси переслать токен в чат».
README, шаг 1, велел ровно обратное: «попроси пользователя написать в чате
Extella „Сгенерируй мне API-токен“, пусть пришлёт строку тебе». Противоречие
внутри единственного входа — и **побеждал README**, потому что промпт сам
отправляет агента читать README как источник правды. Человек, не знающий
Extella, упирался в тупик: где чат, что писать, куда вставлять секрет.

**Просить было не нужно вовсе.** Ключ нужен тот же, что у MCP.

> **ПОПРАВКА 28.09.2026 — два утверждения этого абзаца оказались неверны.**
> Первое: ключ на диске сам НЕ появляется — приложение 1.3.0 его не кладёт, а
> экран выдачи есть (`Library → System → Tokens`), см. H108 и замер 24.09.2026.
> Второе, и оно дороже: **рукопожатие ничего не подтверждает.** `initialize` с
> заведомо неверным ключом отвечает HTTP 200 и `"result"`, а `tools/list`
> отдаёт каталог инструментов вовсе без авторизации. Проверка, построенная на
> подстроке `"result"`, объявляла «подключено» на любой строке вместо ключа —
> и новичок уходил искать поломку там, где её нет (аудит 28.09.2026, F01).
> Доказательство ровно одно: **вызов читающего инструмента и разбор ответа по
> полям** (`isError`, `error`). Пустой список нового аккаунта — законный успех.

**Норма.** Шаг, который человек не может выполнить без знания платформы, —
это не инструкция, а команда: `tools/connect_mcp.py`. Три правила внутри:
1. **Ключ проверяется вызовом, а не наличием файла и не рукопожатием.** Файл
   переживает смену аккаунта, а рукопожатие проходит с любым мусором вместо
   ключа. Честное доказательство — `tools/call` читающего инструмента с
   разбором `isError`.
1-бис. **В заголовках MCP обязателен `X-Agent-Id` — и только в MCP.** Замер
   28.09.2026: вызов `tools/call` с верным ключом, но без этого заголовка
   отвечает `isError: true` и текстом «Failed to resolve dependency 'token'» —
   сообщение винит ключ, хотя ключ верен. **На REST это требование не
   переносится:** `POST /api/agent/list` тем же ключом БЕЗ `X-Agent-Id` отвечает
   HTTP 200. Требование одного заголовка не распространяется на все методы без
   проверки их контрактов. Заголовку достаточно быть непустым (несуществующий идентификатор даёт
   тот же ответ, что настоящий — проверено на `list_agents`; инструменты,
   работающие В области агента, требуют настоящего). Поэтому подключиться можно
   и на пустом аккаунте, а своего агента человек заводит после.
   **Один текст на две причины:** тем же словом MCP отвечает и на неверный
   ключ, и на пустой заголовок агента — по ответу их не различить.
1-тер. **Причину отказа MCP спрашивать у REST.** Замер 28.09.2026: на неверный
   ключ REST отвечает `HTTP 401 {"error":"Invalid or expired token"}`, а MCP в
   ту же секунду — HTTP 200 с текстом про «зависимость token». Честный канал
   есть, и пользоваться надо им: если REST отдаёт 200, ключ ВЕРЕН и чинить надо
   заголовки MCP, а не токен. Пересказывать формулировку MCP как причину
   запрещено — она называет не то, что надо чинить.
1-кватер. **Каким инструментом доказывать — решает замер с неверным ключом.**
   Замер 30.09.2026, живой прогон навыка в сессии Claude Code:
   `get_current_profile_and_agent` «успешно» отвечает НЕВЕРНОМУ ключу — он
   возвращает присланные заголовки, это не доказательство никогда; `list_agents`
   ключ проверяет, но на большом аккаунте отвечает ~270 000 знаков и не влезает
   в вывод инструмента (а с `profile_id: "default"` — 404 «Profile not found»:
   фильтр ждёт настоящий id). Доказательство — `list_profiles` без аргументов:
   неверный ключ отвергает, верному отвечает ~600 знаков. Засчитывается только
   ПОЛОЖИТЕЛЬНЫЙ разобранный ответ (`isError: false` и непустое содержимое):
   «ошибки не видно» — не успех, так «доктор» моста 0.5.0 засчитал недочитанный ответ.
1-квинта. **Claude Code подключается одним путём — плагином моста
   `extella-claude-bridge`** (маркетплейс `AnvarBakiyev/extella-bridges`). До
   30.09.2026 путей было три — свой у установщика стандартов (имя `extella`), свой у
   моста (`extella_acct_…`), старый локальный мост, — и проверка «уже настроен»
   смотрела только на своё имя: у владельца оказались две связки к одному
   аккаунту, одна с ключом открытым текстом в `~/.claude.json`. Теперь формат
   связки живёт только в регистраторе моста (одна связка на аккаунт, аккаунт
   узнаётся по КЛЮЧУ связки, а не по имени; паритет с Node-библиотекой моста держит
   тест), а `tools/connect_mcp.py` ставит плагин и зовёт его регистратор.
2. **Секрет не ложится ни в конфиг, ни в аргументы.** У Claude Code для этого
   есть `headersHelper` — скрипт отдаёт заголовки в момент вызова. У Codex его
   нет, ключ идёт в `~/.codex/config.toml` — файл переводится в 600, и об этом
   сказано вслух, а не умолчано.
3. **Уже настроенное не переписывается**: у человека может быть связка на
   другой аккаунт.

**Мелочь, стоившая бы тишины.** `claude mcp add-json` без `--scope user`
записывает сервер в область ТЕКУЩЕЙ папки (`projects.<cwd>` в `~/.claude.json`).
Агент отчитался бы «подключено», а в любой другой папке связки бы не было.

**Заодно исправлен формат для Codex.** README показывал ему JSON `mcpServers` —
это формат Claude Code. Codex держит MCP в TOML `[mcp_servers.*]`
(`~/.codex/config.toml`); по прежнему примеру он не подключался.
