### H13. ОТМЕНЕНО 13.08.2026 — изоляции по токену больше нет

**Раздел ниже описывает поведение, которого уже не существует.** Оставлен целиком, потому что
на него опирались решения (публикация гида владельцем вручную, чтение токена из отдельного
файла) — и потому что это образцовый пример факта, устаревшего за сутки.

**Замер 13.08.2026, тот же токен устройства:** `my-listings` отдаёт **19 листингов**,
`my-purchases` — **21 покупку**, включая всё, что владелец видел на экране («Тест 1»,
«Recruiter Panel Shell», «Lawyer», «Astra Telecom»). Сутками ранее тот же токен видел **4**.
Что именно изменилось на стороне платформы — не знаю; автор платформы в это время делал
управление токенами с уровнями доступа.

**Действующее правило:** токен аккаунта видит витрину аккаунта. Обходной путь «публикует только
владелец вручную» больше не нужен, отдельный файл с токеном витрины — тоже.

**Что из H13 остаётся полезным:** быстрая диагностика. Если список из API расходится с тем, что
человек видит на экране, — не спорить и не объявлять дефект, а **сверить конкретный
`listing_id`**. У нас на аккаунте живут два разных листинга с похожими именами
(«Predictive Sales» и «Predictive Sales (OSINT)»), и один из них **страницы не имеет вовсе**:
запрос к нему отвечает «This app has no web page». Спутать их — готовый ложный диагноз.

### H13 (исторический текст). Витрина принадлежит ТОКЕНУ, а не аккаунту (12.08.2026)

**Самая дорогая находка дня по потраченному времени.** Я опубликовал приложение, владелец
открыл свой магазин на том же аккаунте — и не увидел его вовсе.

Причина написана в документации платформы, но не читалась как последствие: внутренний ключ
владельца — `sha256(токена)`, и «все пользовательские данные (рабочий стол, покупки, листинги,
баланс) изолированы по владельцу **токена**».

**Значит у одного аккаунта столько параллельных магазинов, сколько у него токенов.** У нашего
живого аккаунта их **одиннадцать** (`list_tokens`): служебные, автосозданные, приглашения
коллегам, сессия тулбара. Публикация служебным токеном ушла в его собственный контейнер:
API честно показывал листинг, интерфейс честно его не показывал — и оба были правы.

Признаки, по которым это видно, а не угадывается:

* одно имя различается между интерфейсом и API (у нас — «Predictive Sales (OSINT)» против
  «Predictive Sales»): это **разные листинги в разных контейнерах**, а не переименование;
* число листингов не совпадает в разы (14 против 4);
* свежеопубликованного нет в интерфейсе, а `my-listings` его отдаёт.

**Правило:** публиковать **тем же токеном**, которым владелец работает в интерфейсе. Токен из
`~/.extella/api_token.txt` для публикации в его витрину **не годится по умолчанию** — сначала
убедись, что это тот самый. Быстрая проверка перед публикацией: сравни `my-listings` с тем, что
владелец видит на экране. Не совпало — не публикуй, спроси.

**Чего делать нельзя:** перебирать токены аккаунта, чтобы найти нужный. Это выглядит и работает
как перебор учётных данных, среда такое останавливает — и правильно. Токены коллег
(`invite: …`) не трогать вовсе: за ними чужие данные.

**Простой обходной путь без токенов вообще:** страничный продукт владелец публикует сам через
форму в ОС — файл интерфейса в поле Web page. Тогда листинг по построению попадает в тот
контейнер, в котором владелец работает.

**Ответ платформы получен 12.08.2026 (автор платформы): так задумано пока.** Готовится
отдельная страница управления токенами с уровнями доступа, и тогда изоляция перестанет быть
проблемой. Значит это **не дефект, а действующая модель** — вопрос закрыт, поднимать заново
не нужно.

До появления той страницы правило выше остаётся в силе: публиковать тем токеном, которым
владелец работает в интерфейсе, а расхождение `my-listings` с экраном считать стоп-сигналом.
Когда управление токенами появится, этот раздел перепроверить: изоляция, скорее всего, станет
настраиваемой, и запрет «не публиковать чужим токеном» превратится в «выбрать нужный уровень
доступа».
