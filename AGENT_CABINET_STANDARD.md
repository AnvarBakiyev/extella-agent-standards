# Стандарт Agent Cabinet (кабинет агента) — часть Extella Evolution

Названия частей системы: `NAMING.md`. Кабинет = **Agent Cabinet**, парк = **Evolution Console**,
полигон = **Evolution Lab**, цикл изменения = **Evolution Loop**, содержание агента = **Agent Genome**.

Владелец: Анвар · Дата: 26.07.2026 · Версия: 1.1
Референс для сравнения: Microsoft Agent 365 (админ-центр управления агентами)

## 1. Зачем

У каждого агента должен быть **свой кабинет** — место, где видно, что это за агент, как он работает
сейчас и как его безопасно менять. Без кабинета агент существует только в голове разработчика: его
нельзя передать другому человеку, показать клиенту или проверить.

Правило: **кабинет не пишется руками для каждого агента.** Он **собирается из паспорта агента**
(`templates/agent_passport.yaml`) генератором `tools/build_agent_cabinet.py`. Путь такой:

```
заполнил паспорт → проверялка пропустила → Agent Cabinet появился сам → агент виден в Evolution Console
```

Следствие: паспорт перестаёт быть «бумажкой для галочки» — он становится источником интерфейса.
Не заполнил границы или пояснение — кабинета нет, выпуска нет.

## 2. Две обязательные части

### 2.1. Agent Passport — «что это и как работает сейчас»

MUST показывать **эффективное состояние**, а не сырые списки объектов платформы:

- стабильный `agent.platform_agent_id` (связь с живым агентом не по имени), цель, роль, владелец,
  рабочий статус, последняя активность;
- live provider и инструкции могут попасть в черновик как `platform_provider` и
  `declared_instructions`; владелец, цель, границы, бюджеты и метрики остаются незаполненными до
  проверки человеком;
- активная версия конфигурации и её неизменяемый идентификатор;
- текущая последовательность действий (заявленная);
- входы, результаты, точки запуска (чат, карточка, расписание, событие, API);
- подключённые модели, интеграции, устройства, интерфейсы;
- действующие знания, правила, способности — **с происхождением каждого элемента**:
  собственный агента / унаследован от группы / общий (влияет на класс), какая версия активна,
  какие этапы работы он меняет;
- права на чтение / подготовку / выполнение;
- последние запуски, ошибки, расходы (**помечать «оценка»**), результаты.

Отдельный блок **«Требует внимания»** (генератор считает его автоматически): общие объекты,
изменение которых затронет другие агенты; действия наружу или с техникой; действия, где
обязателен человек.

Canonical Shared Gene объявляется в верхнем списке `shared_genes` Agent Passport:
`gene_id` (стабильный ключ), `kind` (`knowledge | rule | expert | handler`), `name`, `version`,
`provenance: global`. Потребитель — `agent.platform_agent_id`. Evolution Console считает точное N
потребителей **только по `gene_id`**, не по отображаемому имени. Старое `capability.global` остаётся
видимым для миграции, но не является доказательством общей идентичности объекта.

### 2.2. Два представления поведения — «заявленное» и «фактическое»

MUST быть рядом и сравнимы:

- **«Как должен работать»** — заявленная последовательность и логика (из паспорта);
- **«Как работает фактически»** — маршруты последних управляемых запусков: какие правила сработали,
  какие способности вызывались, на каком шаге агент отклонился от ожидаемого пути.

Это главный смысл кабинета: **красивое описание не доказывает фактическое поведение.**
Расхождение MUST подсвечиваться, а не сглаживаться.

### 2.3. Evolution Loop — управляемое изменение

Цикл (9 шагов, генератор выдаёт его как контракт кабинета): описать словами → определить, что
меняется → выбрать область → создать черновик → показать влияние и зависимости → сравнить прежнюю
и новую версию на одинаковых кейсах → опубликовать → наблюдать → вернуть точную предыдущую версию.

Обязательные ограничения:

- из кабинета одного агента изменение начинается **только для него**;
- при попытке изменить **общий** объект MUST появиться экран влияния: *«Этот механизм используют
  ещё N агентов. Создать локальную версию или изменить весь класс?»* — защита от массовой поломки;
- кабинет использует **тот же журнал версий**, что Evolution Console. Кабинет —
  проекция по одному агенту, а НЕ второй механизм версий;
- кабинет — **зеркало, не второй источник правды**: состояние читается из платформы и журнала;
  расхождение показывается честно («в нашем реестре есть, на платформе нет»), а не подставляется.

### 2.3.1. Создание в Extella из кабинета (решение Анвара 26.07.2026)

Кабинет MUST уметь **создавать в Extella**, а не только показывать. Агент растёт там, где им
управляют: если для добавления знания или способности нужно уходить в другой инструмент, кабинет
остаётся смотровой площадкой, а геном агента развивается мимо управляемого контура.

Создавать MUST быть возможно все четыре вида Agent Genome:

| Что создаём | Что это для владельца агента | Платформа |
|---|---|---|
| **Знание** (Concept) | то, что агент обязан знать | `/api/concept/*` |
| **Правило** (Rule) | что агенту разрешено и запрещено | `/api/rule/*` |
| **Способность** (Expert) | проверяемое действие, которое агент умеет выполнять | `/api/expert/save` |
| **Обработчик класса** (CSPL) | общий способ исполнения целого класса способностей | `/api/expert/save` |

**Обязательные гарантии** — без них создание превращается в тихую запись в чужую область, а это наш
живой класс отказов, не гипотеза:

1. **Тот же Evolution Loop:** черновик → проверка в Evolution Lab → публикация → Evolution Receipt.
   Прямая запись в production из кабинета запрещена.
2. **Область по умолчанию — только этот агент** (§3.6). Общий объект создаётся лишь после экрана
   влияния, и такое создание **завершается в Evolution Console** (§2.4), а не в кабинете.
3. **Запрет дублей имён:** способность с именем, уже существующим в другой области, отклоняется —
   дубль даёт недетерминированный запуск (проверка `wz_expert_janitor`).
4. **Только REST с явно указанной областью.** MCP `save_expert` запрещён: он молча пишет в область
   другого агента.
5. **Только Qwen** для всего, что исполняется.
6. **Успех подтверждается перечитыванием** с платформы (`agent/get`, `experts_db/list`): HTTP 5xx или
   таймаут — не провал и не успех, проверяется артефактом.
7. **Evolution Receipt на каждое создание:** что создано, в какой области, кем и как вернуть
   состояние до создания.
8. **Новый агент в кабинете не создаётся:** кабинет — про одного агента, новый рождается в Evolution
   Console или в Конструкторе (анти-дублирование поверхностей, §2.4).

Контракт машинно-проверяемый: генератор `tools/build_agent_cabinet.py` выдаёт блок
`evolution.creation` (виды, гарантии, область по умолчанию, запреты), и самопроверка это проверяет.
Продукт MUST рендерить именно этот блок, а не собственный список.

## 2.4. Где что живёт: одна механика — два взгляда (решение Анвара 26.07.2026)

Вопрос «всё в Evolution Console или в Agent Cabinet» решается разделением **данных** и
**видов**:

- **Данные и журнал версий живут в ОДНОМ месте.** Один журнал (черновик → тест → публикация →
  откат), одна проекция состояния, один расчёт рисков. Два механизма версий = гарантированное
  расхождение (наш повторяющийся класс отказов: локальный реестр против платформы, оверрайд против
  раздачи).
- **Видов два, и они про разное:**
  - **Evolution Console** — взгляд сверху: весь парк агентов, риски по стандарту, кросс-связи общих
    механизмов, изменения класса, массовые операции.
  - **Agent Cabinet** — взгляд в упор: один агент, его эффективное состояние с происхождением,
    «заявленное против фактического», его локальная эволюция.

**Правило области изменения** (определяет, где изменение завершается):

| Область | Начинается | Завершается |
|---|---|---|
| только этот агент | кабинет | кабинет |
| Shared Gene (класс) | Agent Cabinet — ловит попытку и готовит черновик | **Evolution Console** — тест всего класса, сравнение до/после, поэтапное включение, откат |
| массовая операция | Evolution Console | Evolution Console |

Изменение класса — это переезд (§3.17), и его нельзя завершать из окна одного агента.

**Анти-дублирование (обязательно):**

- в Agent Cabinet MUST NOT быть ничего, чего нет в Evolution Console — кабинет это проекция;
- в Evolution Console MUST NOT быть персонального контекста агента (его последовательности, его
  пояснений) — вместо этого кнопка «Открыть Agent Cabinet»;
- риски считаются **один раз** (проверялкой стандарта); кабинет показывает те же цифры фильтром,
  а не собственный расчёт. Машинный контракт — `check_report(doc)` /
  `check_agent_passport.py --json`; потребитель использует stable issue `code`, а не разбирает
  русский текст. Два разных ответа на один вопрос — дефект.

Масштаб не меняет правило: чем больше агентов, тем важнее Центр; чем важнее конкретный агент, тем
важнее кабинет. Поверхности не конкурируют.

## 3. Честное сравнение с Microsoft Agent 365

| Возможность Agent 365 | У нас сейчас | Комментарий |
|---|---|---|
| Инвентарь агентов организации | **Есть** (проверено вживую: 15 агентов аккаунта) | внутри аккаунта; между аккаунтами платформа видимости не даёт |
| Карточка агента: цель, модель, конфигурация | **Есть** — паспорт + чтение агента с платформы (имя, модель, поставщик, инструкции, инструменты) | |
| Эффективное состояние: знания, правила, способности | **Есть** (проверено: 155 знаний, 73 правила, 916 способностей) | с происхождением и активной версией |
| Активность: сессии, ошибки, активные пользователи | **Частично** — по управляемым запускам и квитанциям | прямые чаты с агентом не видны: нативной трассировки нет |
| Расходы | **Оценка** | не биллинговый факт; помечать словом «оценка» |
| Экспорт | **Есть** (CSV/JSON из данных кабинета) | |
| «Риски агентов», «бесхозные агенты» | **Есть, и осмысленнее** — это результат нашей проверялки стандарта | агент без владельца, без границ, без отката, не на Qwen, с мёртвыми ссылками = в списке рисков |
| Блокировка / отключение агента | **Локально** (расписания, карточки, наш контур) | платформенной блокировки нет |
| Роли и права (Users / Permissions) | **Нет** | ждёт платформенной модели ролей (эскалация A4) |
| Безопасность и соответствие, защищённый от подделки аудит | **Нет** | журнал есть, tamper-evident нет |
| Сквозная трассировка «агент вызвал агента» | **Частично** | платформенной трассировки нет |

Правило подачи: то, чего у нас нет, MUST быть названо в интерфейсе кабинета как граница, а не
скрыто. Кабинет, обещающий полную картину без неё, — та же ложь, против которой он задуман.

## 4. Базовая технология (делаем сами, лежит в этом репозитории)

| Файл | Роль |
|---|---|
| `templates/agent_passport.yaml` | источник истины о агенте; stable platform ID и canonical Shared Genes |
| `tools/check_agent_passport.py` | единый гейт + двуязычный structured report с stable issue codes |
| `tools/build_agent_cabinet.py` | **генератор Agent Cabinet из Agent Passport**, схема `extella.agent_cabinet.v1.1` |
| `templates/cabinet_widget.js` | XSS-safe рендер: Agent Passport / фактическое поведение / Evolution Loop, RU+EN |
| `templates/help_card.md`, `templates/help_widget.js` | XSS-safe пояснение «? Как это работает», RU+EN |
| `tools/test_widgets.js` | render/security selftest трёх вкладок и пояснения |

Продуктовая часть (Evolution Console, живые данные, публикация версий) реализуется
в продукте и MUST использовать эти артефакты, а не собственные копии.

## 5. Критерий готовности кабинета

- Кабинет собран **генератором из паспорта**, а не написан руками.
- Agent Passport связан с живым агентом через stable `platform_agent_id`, не через имя.
- Shared Genes имеют stable `gene_id`; точное N потребителей не считается по именам.
- Видны эффективное состояние с происхождением и активная версия.
- «Заявленное» и «фактическое» рядом, расхождение подсвечено.
- Изменение общего объекта невозможно без экрана влияния и выбора «локально / весь класс».
- **Из кабинета можно СОЗДАТЬ в Extella** знание, правило, способность и обработчик класса (§2.3.1) —
  тем же Evolution Loop, по умолчанию только для этого агента, с квитанцией и откатом. Создание
  нового агента в кабинете отсутствует.
- Откат возвращает точную предыдущую версию, история и квитанции сохраняются.
- Границы (раздел 3) присутствуют **в интерфейсе**, а не только в документации.
- Пояснение «? Как это работает» и весь интерфейс — **на русском и английском** (§3.26).
