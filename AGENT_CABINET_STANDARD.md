# Стандарт Agent Cabinet (кабинет агента) — часть Extella Evolution

Названия частей системы: `NAMING.md`. Кабинет = **Agent Cabinet**, парк = **Evolution Console**,
полигон = **Evolution Lab**, цикл изменения = **Evolution Loop**, содержание агента = **Agent Genome**.

Владелец: Анвар · Дата: 09.08.2026 · Версия: 1.2
Референс для сравнения: Microsoft Agent 365 (админ-центр управления агентами)

## 1. Зачем

У каждого агента должен быть **свой кабинет** — место, где видно, что это за агент, как он работает
сейчас и как его безопасно менять. Без кабинета агент существует только в голове разработчика: его
нельзя передать другому человеку, показать клиенту или проверить.

Правило: **кабинет не пишется руками для каждого агента.** Он **собирается из паспорта агента**
(`templates/agent_passport.yaml`) генератором `tools/build_agent_cabinet.py`. Путь такой:

```
заполнил паспорт → проверялка пропустила → Agent Cabinet появился сам → агент виден в Evolution Console
```

Следствие: паспорт перестаёт быть «бумажкой для галочки» — он становится источником интерфейса.
Не заполнил границы или пояснение — кабинета нет, выпуска нет.

## 2. Две обязательные части

### 2.1. Agent Passport — «что это и как работает сейчас»

MUST показывать **эффективное состояние**, а не сырые списки объектов платформы:

- стабильный `agent.platform_agent_id` (связь с живым агентом не по имени), цель, роль, владелец,
  рабочий статус, последняя активность;
- live provider и инструкции могут попасть в черновик как `platform_provider` и
  `declared_instructions`; владелец, цель, границы, бюджеты и метрики остаются незаполненными до
  проверки человеком;
- активная версия конфигурации и её неизменяемый идентификатор;
- текущая последовательность действий (заявленная);
- входы, результаты, точки запуска (чат, карточка, расписание, событие, API);
- подключённые модели, интеграции, устройства, интерфейсы;
- действующие знания, правила, способности — **с происхождением каждого элемента**:
  собственный агента / унаследован от группы / общий (влияет на класс), какая версия активна,
  какие этапы работы он меняет;
- права на чтение / подготовку / выполнение;
- последние запуски, ошибки, расходы (**помечать «оценка»**), результаты.

Отдельный блок **«Требует внимания»** (генератор считает его автоматически): общие объекты,
изменение которых затронет другие агенты; действия наружу или с техникой; действия, где
обязателен человек.

Canonical Shared Gene объявляется в верхнем списке `shared_genes` Agent Passport:
`gene_id` (стабильный ключ), `kind` (`knowledge | rule | expert | handler`), `name`, `version`,
`provenance` со значением `global`. Потребителем выступает стабильный id агента. Evolution Console считает точное N
потребителей **только по `gene_id`**, не по отображаемому имени. Старое `capability.global` остаётся
видимым для миграции, но не является доказательством общей идентичности объекта.

### 2.2. Два представления поведения — «заявленное» и «фактическое»

MUST быть рядом и сравнимы:

- **«Как должен работать»** — заявленная последовательность и логика (из паспорта);
- **«Как работает фактически»** — маршруты последних управляемых запусков: какие правила сработали,
  какие способности вызывались, на каком шаге агент отклонился от ожидаемого пути.

Это главный смысл кабинета: **красивое описание не доказывает фактическое поведение.**
Расхождение MUST подсвечиваться, а не сглаживаться.

### 2.3. Evolution Loop — управляемое изменение

Цикл (9 шагов, генератор выдаёт его как контракт кабинета): описать словами → определить, что
меняется → выбрать область → создать черновик → показать влияние и зависимости → сравнить прежнюю
и новую версию на одинаковых кейсах → опубликовать → наблюдать → вернуть точную предыдущую версию.

Обязательные ограничения:

- из кабинета одного агента изменение начинается **только для него**;
- при попытке изменить **общий** объект MUST появиться экран влияния: *«Этот механизм используют
  ещё N агентов. Создать локальную версию или изменить весь класс?»* — защита от массовой поломки;
- кабинет использует **тот же журнал версий**, что Evolution Console. Кабинет —
  проекция по одному агенту, а НЕ второй механизм версий;
- кабинет — **зеркало, не второй источник правды**: состояние читается из платформы и журнала;
  расхождение показывается честно («в нашем реестре есть, на платформе нет»), а не подставляется.

### 2.3.1. Создание в Extella из кабинета (решение Анвара 26.07.2026)

Кабинет MUST уметь **создавать в Extella**, а не только показывать. Агент растёт там, где им
управляют: если для добавления знания или способности нужно уходить в другой инструмент, кабинет
остаётся смотровой площадкой, а геном агента развивается мимо управляемого контура.

Создавать MUST быть возможно все четыре вида Agent Genome:

| Что создаём | Что это для владельца агента | Платформа |
|---|---|---|
| **Знание** (Concept) | то, что агент обязан знать | `/api/concept/*` |
| **Правило** (Rule) | что агенту разрешено и запрещено | `/api/rule/*` |
| **Способность** (Expert) | проверяемое действие, которое агент умеет выполнять | `/api/expert/save` |
| **Обработчик класса** (CSPL) | общий способ исполнения целого класса способностей | `/api/expert/save` |

**Обязательные гарантии** — без них создание превращается в тихую запись в чужую область, а это наш
живой класс отказов, не гипотеза:

1. **Тот же Evolution Loop:** черновик → проверка в Evolution Lab → публикация → Evolution Receipt.
   Прямая запись в production из кабинета запрещена.
2. **Область по умолчанию — только этот агент** (§3.6). Общий объект создаётся лишь после экрана
   влияния, и такое создание **завершается в Evolution Console** (§2.4), а не в кабинете.
3. **Запрет дублей имён:** способность с именем, уже существующим в другой области, отклоняется —
   дубль даёт недетерминированный запуск (проверка `wz_expert_janitor`).
4. **Только REST с явно указанной областью.** MCP `save_expert` запрещён: он молча пишет в область
   другого агента.
5. **Только Qwen** для всего, что исполняется.
6. **Успех подтверждается перечитыванием** с платформы (`agent/get`, `experts_db/list`): HTTP 5xx или
   таймаут — не провал и не успех, проверяется артефактом.
7. **Evolution Receipt на каждое создание:** что создано, в какой области, кем и как вернуть
   состояние до создания.
8. **Новый агент в кабинете не создаётся:** кабинет — про одного агента, новый рождается в Evolution
   Console или в Конструкторе (анти-дублирование поверхностей, §2.4).

Контракт машинно-проверяемый: генератор `tools/build_agent_cabinet.py` выдаёт блок
`evolution.creation` (виды, гарантии, область по умолчанию, запреты), и самопроверка это проверяет.
Продукт MUST рендерить именно этот блок, а не собственный список.

## 2.4. Где что живёт: одна механика — два взгляда (решение Анвара 26.07.2026)

Вопрос «всё в Evolution Console или в Agent Cabinet» решается разделением **данных** и
**видов**:

- **Данные и журнал версий живут в ОДНОМ месте.** Один журнал (черновик → тест → публикация →
  откат), одна проекция состояния, один расчёт рисков. Два механизма версий = гарантированное
  расхождение (наш повторяющийся класс отказов: локальный реестр против платформы, оверрайд против
  раздачи).
- **Видов два, и они про разное:**
  - **Evolution Console** — взгляд сверху: весь парк агентов, риски по стандарту, кросс-связи общих
    механизмов, изменения класса, массовые операции.
  - **Agent Cabinet** — взгляд в упор: один агент, его эффективное состояние с происхождением,
    «заявленное против фактического», его локальная эволюция.

**Правило области изменения** (определяет, где изменение завершается):

| Область | Начинается | Завершается |
|---|---|---|
| только этот агент | кабинет | кабинет |
| Shared Gene (класс) | Agent Cabinet — ловит попытку и готовит черновик | **Evolution Console** — тест всего класса, сравнение до/после, поэтапное включение, откат |
| массовая операция | Evolution Console | Evolution Console |

Изменение класса — это переезд (§3.17), и его нельзя завершать из окна одного агента.

**Анти-дублирование (обязательно):**

- в Agent Cabinet MUST NOT быть ничего, чего нет в Evolution Console — кабинет это проекция;
- в Evolution Console MUST NOT быть персонального контекста агента (его последовательности, его
  пояснений) — вместо этого кнопка «Открыть Agent Cabinet»;
- риски считаются **один раз** (проверялкой стандарта); кабинет показывает те же цифры фильтром,
  а не собственный расчёт. Машинный контракт — `check_report(doc)` /
  `check_agent_passport.py --json`; потребитель использует stable issue `code`, а не разбирает
  русский текст. Два разных ответа на один вопрос — дефект.

Масштаб не меняет правило: чем больше агентов, тем важнее Центр; чем важнее конкретный агент, тем
важнее кабинет. Поверхности не конкурируют.

## 3. Честное сравнение с Microsoft Agent 365

| Возможность Agent 365 | У нас сейчас | Комментарий |
|---|---|---|
| Инвентарь агентов организации | **Есть** (проверено вживую: 15 агентов аккаунта) | внутри аккаунта; между аккаунтами платформа видимости не даёт |
| Карточка агента: цель, модель, конфигурация | **Есть** — паспорт + чтение агента с платформы (имя, модель, поставщик, инструкции, инструменты) | |
| Эффективное состояние: знания, правила, способности | **Есть** (проверено: 155 знаний, 73 правила, 916 способностей) | с происхождением и активной версией |
| Активность: сессии, ошибки, активные пользователи | **Частично** — по управляемым запускам и квитанциям | прямые чаты с агентом не видны: нативной трассировки нет |
| Расходы | **Оценка** | не биллинговый факт; помечать словом «оценка» |
| Экспорт | **Есть** (CSV/JSON из данных кабинета) | |
| «Риски агентов», «бесхозные агенты» | **Есть, и осмысленнее** — это результат нашей проверялки стандарта | агент без владельца, без границ, без отката, не на Qwen, с мёртвыми ссылками = в списке рисков |
| Блокировка / отключение агента | **Локально** (расписания, карточки, наш контур) | платформенной блокировки нет |
| Роли и права (Users / Permissions) | **Нет** | ждёт платформенной модели ролей (эскалация A4) |
| Безопасность и соответствие, защищённый от подделки аудит | **Нет** | журнал есть, tamper-evident нет |
| Сквозная трассировка «агент вызвал агента» | **Частично** | платформенной трассировки нет |

Правило подачи: то, чего у нас нет, MUST быть названо в интерфейсе кабинета как граница, а не
скрыто. Кабинет, обещающий полную картину без неё, — та же ложь, против которой он задуман.

## 5. Критерий готовности кабинета

- Кабинет собран **генератором из паспорта**, а не написан руками.
- Agent Passport связан с живым агентом через stable `platform_agent_id`, не через имя.
- Shared Genes имеют stable `gene_id`; точное N потребителей не считается по именам.
- Видны эффективное состояние с происхождением и активная версия.
- «Заявленное» и «фактическое» рядом, расхождение подсвечено.
- Изменение общего объекта невозможно без экрана влияния и выбора «локально / весь класс».
- **Из кабинета можно СОЗДАТЬ в Extella** знание, правило, способность и обработчик класса (§2.3.1) —
  тем же Evolution Loop, по умолчанию только для этого агента, с квитанцией и откатом. Создание
  нового агента в кабинете отсутствует.
- Откат возвращает точную предыдущую версию, история и квитанции сохраняются.
- Границы (раздел 3) присутствуют **в интерфейсе**, а не только в документации.
- Пояснение «? Как это работает» и весь интерфейс — **на русском и английском** (§3.26).

## 6. Автоматизация — главный объект, агенты внутри — компоненты (решение Анвара 26.07.2026)

Клиент покупает и устанавливает **автоматизацию** (Агент 1С, Kazakh Lawyer, турагентство), а не
«агента Extella». Поэтому главный объект Evolution Console — автоматизация, а платформенные агенты
внутри неё — **скрытые технические компоненты**.

Пробел, который это закрывает: паспорт агента описывает ОДИН агент (`platform_agent_id` — одна
строка), составная автоматизация им не описывалась.

| Объект | Файл | Проверялка | Генератор кабинета |
|---|---|---|---|
| агент | `templates/agent_passport.yaml` | `tools/check_agent_passport.py` | `tools/build_agent_cabinet.py` (`extella.agent_cabinet.v1.1`) |
| **автоматизация** | `templates/automation_passport.yaml` | `tools/check_automation_passport.py` (самопроверка 49/49) | `tools/build_automation_cabinet.py` (`extella.automation_cabinet.v1`, самопроверка 17/17) |
| **ответ `/api/state`** | отдаёт сама служба | `tools/check_state_contract.py` (самопроверка 13/13) | — |

Обязательное в паспорте автоматизации:

1. **стабильный `automation_id`** — не имя и не путь; по имени связывать запрещено;
2. **контракт состояния** `service.health` + `service.state` — без него Console показывала бы
   «порт отвечает» как «работает»;
3. **состав**: платформенные агенты (каждый — со стабильным `component_id`, фактическим
   `platform_agent_id` или `USER_SELECTED` и ожидаемым провайдером `alibaba`), способности,
   расписания с явным видом (`external_cron | internal | in_service`),
   интеграции с ПРАВАМИ (см. §6.2), знания, правила;
4. **границы** `limits` и **пояснение** `help_surface` — те же правила, что у агента (§3.20);
5. **два языка** в названии и описаниях (§3.26);
6. **эксплуатация**: дежурный, путь отката, метрика успеха;
7. **`hosting_profile`** (`local | server | client_server`) — где автоматизация живёт. У серверных
   нет каталога на диске, и без этого поля джанитор удаляет их карточку как «мёртвую».

Гейты, которые работают машинно:

- агент-компонент **не на Qwen** → паспорт не проходит, кабинет не собирается (канон
  «клиентские агенты только платформенный Qwen»);
- **дубль агента** в составе → ошибка: потребители считаются по id, дубль ломает счёт;
- **паспорт без границ** → кабинета нет, как и у агента;
- **неизвестный вид расписания** → ошибка: Console обязана знать, где живёт тик;
- **размещение не указано или неизвестно** → ошибка (пункт 7 выше).

### 6.0б. Состояние читает ЭКСПЕРТ, а не порт (решение 06.08.2026)

Console работает на чужой машине. Порт `127.0.0.1` там либо молчит, либо отвечает чужой
процесс — оба случая Console обязана отличать от «работает». Поэтому у паспорта
автоматизации есть предпочтительный источник состояния — эксперт на устройстве:

| Поле `automation.state_reader` | Что объявляет |
|---|---|
| `expert` | имя эксперта-диспетчера, который отдаёт состояние |
| `method` | метод внутри диспетчера, если у продукта есть таблица маршрутов |
| `schema` | контракт ответа; незнакомая схема = «состояние недоступно», а не умолчания |
| `agent_scope` | как получить `X-Agent-Id`: `AGENT_FROM_COMPONENT` / `AGENT_USER_SELECTED` / `ACCOUNT_GLOBAL` |
| `agent_scope_ref` | стабильный `component_id` из состава; обязателен для первых двух режимов, запрещён для `ACCOUNT_GLOBAL` |
| `expert_global` | точный флаг `global` Expert; обязательный boolean, не выводится из скоупа заголовка |
| `execution_device` | стабильный id таргета, НА КОТОРОМ исполняется эксперт |
| `data_device` | стабильный id таргета, ГДЕ лежат данные (у Баға это разные машины) |
| `evidence` | сегодня единственное допустимое значение — `exact_target` |

Правила, проверяемые машинно (`tools/check_automation_passport.py`):

- обязателен ХОТЯ БЫ ОДИН источник состояния: `state_reader` или `service`;
- устройство — это стабильный id таргета; `localhost`, `127.0.0.1` и порт как значение
  устройства запрещены;
- у продукта только с `service` появляется предупреждение: состояние читается по
  localhost, а у коллеги и на сервере клиента этого порта нет;
- `evidence` обязателен, потому что закрепление одиночным `target` платформа игнорирует
  МОЛЧА: вызов идёт массивом `targets`, а ответ обязан нести id устройства.

**Ссылка на агентский скоуп идёт через компонент, не через индекс и не через второй agent id.**
Каждый элемент `components.platform_agents[]` получает непустой строковый `component_id`,
уникальный в пределах паспорта. `agent_scope_ref` ссылается только на него: перестановка состава
не ломает ссылку, а `platform_agent_id` продолжает жить в одном месте.

Три режима закрыты:

- `AGENT_FROM_COMPONENT` ссылается на компонент с точным `platform_agent_id` вида `agent_...`;
- `AGENT_USER_SELECTED` ссылается на компонент с `platform_agent_id: USER_SELECTED`. У компонента
  обязателен точный локатор `binding_ref` формы `<путь>:<поле>`, например
  `~/extella_baga/agent_binding.json:agent_id`; путь без имени поля не разрешает привязку;
- `ACCOUNT_GLOBAL` не несёт `agent_scope_ref` и допустим только с `expert_global: true`.

Для двух компонентных режимов `expert_global` ортогонален скоупу: и `false`, и `true` допустимы,
потому что в проде существуют оба сочетания. Флаг нельзя выводить из `agent_scope`.

Переход fail-closed: отсутствие `agent_scope` пока даёт одно предупреждение
`AUTOMATION_STATE_SCOPE_REQUIRED`, а Console показывает `STATE_READER_SCOPE_UNAVAILABLE` и не
выбирает первого агента. Как только поле объявлено, неверные значения — ошибки:
`AUTOMATION_STATE_SCOPE_INVALID`, `AUTOMATION_STATE_SCOPE_REF_REQUIRED`,
`AUTOMATION_STATE_SCOPE_REF_UNRESOLVED`, `AUTOMATION_STATE_SCOPE_BINDING_REQUIRED`,
`AUTOMATION_STATE_SCOPE_REF_FORBIDDEN`. Структуру v2 дополнительно защищают
`AUTOMATION_AGENT_COMPONENT_ID_REQUIRED`, `AUTOMATION_AGENT_COMPONENT_ID_DUPLICATE`,
`AUTOMATION_STATE_EXPERT_GLOBAL_REQUIRED`, `AUTOMATION_STATE_EXPERT_GLOBAL_INVALID`.
После миграции шести продуктов предупреждение `AUTOMATION_STATE_SCOPE_REQUIRED` повышается до ошибки.

### 6.0в. Класс поверхности: что вообще показывать в парке

Не всё установленное — автоматизация клиента. Класс объявлен один раз в
`surface_classes.yaml` и проверяется гейтом `tools/check_surface_classes.py`:

| Класс | Что это | Нужен ли Automation Passport |
|---|---|---|
| `automation` | то, что клиент купил и установил | **да**, и он обязан проходить гейт |
| `system` | платформенная поверхность Extella (Конструктор, Подключения, Workspace, Второй пилот, Студии, Команда, сервис обезличивания) | нет — это часть инструмента |
| `installed_app` | стороннее приложение, установленное пользователем через витрину | нет — мы за него не отвечаем |
| `probe` | наша временная проба | нет — в парке клиента ей не место |

Гейт также сверяет `registry_card_id`: id карточки на устройстве может отличаться от
`automation_id` (Баға стоит карточкой `baga_thin`), и без явной связки обе стороны выглядят
как мёртвая ссылка.

### 6.0г. Точная форма `extella.automation_state.v1`

Схема объявляется в `automation.state_reader.schema`; сам payload не получает второй
дискриминатор. Все восемь полей верхнего уровня обязательны, но их значения не свободны:

| Поле | Допустимое значение |
|---|---|
| `enabled` | только boolean `true` / `false`; строка `"true"` и `null` не являются фактом |
| `active_version` | SemVer 2.0.0 строка или `null` |
| `last_run` | ISO 8601 строка, конечное число, объект с корректным `at` или `ts`, либо `null` |
| `last_result` | закрытый enum `ok` / `failed` / `partial` либо `null` |
| `last_error` | `{code, message_ru, message_en}` с тремя непустыми строками либо `null` |
| `schedules` | массив; каждый элемент содержит непустой `id`, boolean `active` и присутствующий `next_run` типа строка / конечное число / `null` |
| `checked_at` | корректная ISO 8601 строка либо `null` |
| `bound_to` | объект точной формы из §6.1; сам объект не бывает `null` |

Дополнительные продуктовые поля допустимы. Они не заменяют канонические поля и не позволяют
выводить их по косвенным признакам. Для числовых меток `bool` не считается числом, `NaN` и
бесконечность запрещены. У `last_run` с обоими ключами `at` имеет приоритет: неверный `at`
нельзя скрыть корректным `ts`.

### 6.1. Привязка `bound_to` в ответе `/api/state` (пункт A2)

Клиент, купивший автоматизацию, обязан видеть не «работает», а **«работает, сервер такой-то,
аккаунт такой-то, агент такой-то, версия такая-то»**. Иначе он не отличит свой контур от чужого,
и выдача теряет смысл. Поэтому ответ `/api/state` обязан содержать блок `bound_to`:

| Поле | Что значит |
|---|---|
| `hosting_profile` | точный enum `local` / `server` / `client_server` либо `null` |
| `host` | непустой адрес, по которому служба отвечает, либо `null` |
| `platform_profile_id` | непустой профиль платформы, под которым автоматизация ходит в API, либо `null` |
| `account_ref` | **короткий необратимый отпечаток аккаунта** (8–32 lowercase hex) либо `null`, НЕ токен |
| `agent_ids` | список уникальных стабильных `agent_...` id либо `null`; пустой список — честный факт отсутствия привязки |
| `since` | корректная ISO 8601 дата привязки либо `null` |

Четыре правила, которые проверяются машинно (`tools/check_state_contract.py`):

1. **Отсутствие поля и честное «неизвестно» — разные вещи.** Поле обязано присутствовать; `null`
   внутри — допустимый ответ, отсутствие поля — ошибка. Это то же правило, что не даёт Console
   выдавать подстановку за факт.
2. **Секретам в состоянии не место.** Состояние отдаётся клиенту, поэтому `account_ref` — только
   отпечаток, а любая строка в блоке, похожая на живой токен, роняет проверку.
3. **`bound_to` отдаёт факт, а не намерение.** Если агент не привязан, список пуст; расхождение с
   паспортом показывает Console, а не прячет служба.
4. **Тип не угадывается.** Число вместо строки, строка вместо списка, пробельная строка и
   регистронезависимая подстановка вроде `LOCAL` являются ошибками контракта, а не значениями,
   которые потребитель должен чинить сам.

### 6.2. Права коннекторов в паспорте (пункт A4)

Корпоративный клиент проходит проверку безопасности **по паспорту, не читая наш код**. Поэтому
каждая запись `components.integrations[]` объявляет права, а не только факт записи наружу:

| Поле | Обязательно | Смысл |
|---|---|---|
| `kind` | да | какая внешняя система |
| `scopes` | да | что именно разрешено (`messages.read`, `rows.write`, …) |
| `personal_data` | да | `none` / `reads` / `stores` — **умолчания нет** |
| `retention` | при `stores` | сколько хранятся ПДн — нужно для договора об обработке |
| `human_in_loop` | при записи наружу | подтверждает ли человек; ответ «нет» допустим, молчание — нет |
| `secret_ref` | желательно | ГДЕ лежит секрет; сам секрет в паспорте = ошибка |
| `account`, `external_writes` | желательно | чей доступ используется и пишет ли наружу |

Смысл жёсткости: «не сказано» — это не «не трогает». Паспорт, в котором права коннектора не
видны, скрывает ровно то, ради чего клиент его читает.

Кабинет автоматизации **собирается генератором** и содержит: состав (агенты помечены как
`surface: component` с входом в их Agent Cabinet), объявленный контракт состояния с честным
«состояние недоступно», автоматически посчитанный блок внимания (что пишет наружу, какие тики
внешние) и границы на двух языках. Кабинеты агентов-компонентов собираются **тем же** генератором
агента — композиция, а не второй механизм.

Проверено на живом продукте 26.07.2026: паспорт турагентства (`extella_travel_agency`, агент
«Travel agent» на Qwen, два расписания, WhatsApp с записью наружу) проходит гейт и даёт кабинет.

## 7. Где живут реестры (решение Анвара 28.07.2026)

Правило, из которого следует всё остальное:

> **Реестр можно хранить только там, откуда его можно пересобрать. Если потеря хранилища
> означает потерю данных, это не реестр, а единственная копия.**

Повод — инцидент 28.07: реестр автоматизаций читался пустым, хотя 12 записей были целы. Они
лежали в чужом скоупе KV, и `global: true` их не доставал: **собственная копия ключа у агента
побеждает общую, молча и с успешным ответом**. Доказано на `composer:catalog` — один и тот же
запрос отдаёт одному агенту 25 блоков, другому его личные 13. Дубли нашлись у 17 ключей из 121.

Поэтому реестры разделяются по тому, **кто владеет правдой**:

| Уровень | Что там | Где живёт | Роль |
|---|---|---|---|
| 1 | что вообще существует | **паспорта в git** | ИСТОЧНИК ПРАВДЫ: ревью, версии, откат |
| 2 | что установлено здесь | файлы на устройстве + контракт `/api/state` | факт этой установки |
| 3 | что агент может найти | собранный реестр | ПРОИЗВОДНАЯ, пересобирается одной командой |

За KV остаётся одна честная роль — **кэш и память агента**. Реестр в KV не хранится: потеря
кэша обязана быть безболезненной.

Сборка третьего уровня: `tools/build_capability_registry.py` (схема `extella.capability_registry.v1`,
самопроверка 10/10). Он **не прячет проблемы**: паспорт, не прошедший гейт, попадает в реестр с
`passport_ok: false` и кодами ошибок; один `automation_id` в нескольких паспортах — предупреждение;
способность, объявленная несколькими автоматизациями, помечается кандидатом в общие.

Первый живой прогон 28.07 (каноничные репозитории): автоматизаций объявлено **2** — турагентство
проходит, Агент 1С нет; Kazakh Lawyer в реестре отсутствует, паспорта у него нет. Способностей
объявлено **4** при 716 экспертах на аккаунте. Это и есть честная мера сегодняшней связности.
