# Extella — онбординг для AI-агента (Codex / Claude / любой LLM-ассистент)

Этот документ — сжатый опыт нескольких недель реальной стройки на Extella (Adoption Wizard, тулбар, паки Travel Agency / Competitor Intel / Legal). Прочитай целиком ПЕРЕД первым действием. Здесь всё, на чём мы уже обжигались. Документ внутренний, НЕ публиковать.

## 1. Что такое Extella (за 60 секунд)

Extella — платформа корпоративных ИИ-агентов: облако (api.extella.ai) + десктоп-приложение (Extella Desktop, Electron) + **listener** на устройствах клиента (демон, исполняющий код локально). Ключевые сущности:

| Сущность | Что это | Где живёт |
|---|---|---|
| **Агент** | LLM с инструкциями и инструментами (модель Qwen 3.7 или Claude) | облако |
| **Эксперт** | Именованная функция на «fython» (python-диалект), запускается облаком или на устройстве через listener | облако; исполняется где скажешь |
| **Концепт** | Единица знаний с эмбеддингом (семантический поиск) | облако |
| **Правило** | Поведенческое правило агента | облако |
| **KV** | Ключ-значение хранилище (`/api/kv/*`) — конфиги, каталоги, расписания, очереди | облако |
| **Target** | Устройство с listener'ом (UUID); эксперт можно направить на конкретный target | устройства |
| **Профиль** | Рабочее пространство аккаунта (обычно `default`) | облако |

## 2. ЖЕЛЕЗНЫЙ КАНОН (нарушение = сломанный прод или деньги клиента)

1. **Все клиентские агенты — платформенный Qwen 3.7.** `agent_extella_default` — это Claude Sonnet, он ПЛАТНЫЙ: не использовать его как «дефолт» и не гонять на нём циклы. BYOK/gpt-4o в клиентских сценариях запрещены.
2. **Агентов НЕ создавать по API.** `POST /api/agent/create` всегда делает Pro-BYOK-агента → при запуске `pro_key_required`. Единственный рабочий путь: человек в UI делает «копировать» базового Qwen-агента (2 клика) и передаёт тебе id. Проси id, не пытайся создать сам.
3. **Скоупинг: всё общее — `global: true`**, и сохранять, и вызывать. Один и тот же expert_name в двух скоупах = недетерминированный запуск (какой из двух выполнится — лотерея). Проверка дублей: эксперт `wz_expert_janitor`.
4. **Продовые агенты заморожены.** Изменения процессов — только через агента-Строителя с записью решения в сессию (`~/extella_wizard/sessions/`). Письма/внешние отправки — только черновики, отправляет человек.
5. **Файлы = источник истины.** Инструкции агентов и код экспертов канонически живут файлами в git (`adoption_wizard/*_instructions.md`, `experts/*.py`). Порядок: правишь файл → прошиваешь платформу целиком → коммит. Никаких правок «только на платформе».
6. **Секреты не хардкодить и не печатать.** Токен Extella берётся из `~/extella_wizard/app/config.json` (или у владельца). В логи, чаты, коммиты — никогда (перед пушем скрабить). Учти: listener сам печатает токен в debug-логи (известный баг) — логи не публиковать.

## 3. REST API — шпаргалка и ловушки

База: `https://api.extella.ai`. Заголовки: `X-Auth-Token`, `X-Profile-Id: default`, `X-Agent-Id` (для запуска агента).

- Пути в **единственном числе**: `/api/agent/run`, `/api/expert/run`, `/api/expert/save`, `/api/kv/get|set|search`; задачи — во множественном: `/api/tasks/check`.
- **Исключение**: список экспертов — `/api/experts_db/list`.
- **[обновлено 23.07, live] `/api/agent/get` ОТДАЁТ `instructions` и `tools`** (проверено: 14.8K символов инструкций, 47 инструментов) — агента можно читать: бэкап, аудит, детект дрейфа. Файлы в git остаются источником истины, но верификация чтением теперь возможна.
- **[обновлено 23.07] `agents/list`** команда чинила; на нашем аккаунте ранее видели пусто — перед использованием проверь на своём токене, фолбэк — id в конфиге.
- MCP-эндпоинт: `https://api.extella.ai/mcp/` (**streamable-http**; старый SSE `/sse/` — legacy). Если MCP-мост глючит на save_expert — фолбэк на REST `/api/expert/save` работает всегда.

### Асинхронные задачи
**[обновлено 23.07, live]** Долгий `expert/run` уходит в deferred и **возвращает `task_id` прямо в ответе** (поле `task_id` + `result: "deferred, use task_id as reference"`); поллить `/api/tasks/check` (мн. число!). Статусы во время выполнения теперь **честные `running`** (старые `time:<timestamp>`-хартбиты убраны — проверено тремя опросами живой задачи). Учти: клиентский таймаут < ~50с не даст дождаться deferred-ответа — жди минимум 60–90с.

### Транзиентные ошибки
**HTTP 500 / timeout ≠ провал.** Операция часто реально проходит. Правило: проверяй артефактами (создался ли эксперт, записался ли KV) и ретрай идемпотентно. Ошибки часто непрозрачны (`empty output`, 500 без деталей) — диагностируй по следам, не по тексту ошибки.

## 4. Агенты по API — правила выживания

**[ЖИВАЯ ПРОВЕРКА 23.07 — три старых костыля сняты, техотдел починил в проде:]**
1. **Мульти-тул РАБОТАЕТ: 2+ инструмента за ход, аргументы НЕ склеиваются** (проверено: два run_expert с разными params в одном ходе — оба получили свои). Правило «один инструмент за ход» из инструкций агентов можно снимать (постепенно, с прогоном).
2. **`recursion_limit` принимается параметром** в теле `agent/run` (проверено на 80; полный прогон >50 шагов ещё не гоняли — при первом длинном таске проверь).
3. **`previous_response_id` работает** (память диалога: слово из хода 1 воспроизведено в ходе 2 по rid). Самодостаточные сообщения остаются хорошей практикой для устойчивости к обрывам, но это больше не обязательный костыль.
4. **`background: true` в agent/run ИГНОРИРУЕТСЯ** (эхо `background: false`) — честного async на агентских ходах всё ещё нет; для долгих агентских работ по-прежнему дробить/поллить артефакты.
5. **Keyless-разговоры**: раньше платформа не хранила их (`store:false`); после фикса `previous_response_id` память через `store:true` + rid работает — но стенограмма-файл (`sessions/<sid>_chat.json`) остаётся надёжным фолбэком.
6. **Потолок вывода fine-tune ~22K символов.** Большие JSON-планы обрезаются. Проси `max_output_tokens: 16000`+, дроби вывод, валидируй JSON и перезапрашивай хвост.
7. Большой inline-результат эксперта может не доехать («Task completed but upload result failed») — пиши результат в файл (`output_path`) и возвращай компактную сводку.

## 5. Эксперты — как писать правильно

### Обычные (fython) эксперты
```python
$extens("include.py")
include("import requests", ["extella-pip install requests"])

def my_expert(param: str = "", api_token: str = "") -> dict:
    """Описание — первая строка docstring попадает в каталог."""
    ...
    return {"ok": True}
```
- **Зависимости ТОЛЬКО через `include("import X", ["extella-pip install X"])`.** Голый `try/except ImportError` умирает на чистой среде клиента.
- Сохранение: `/api/expert/save` c `global: true`; после сохранения — **verify**: скачай эксперта обратно (`get_expert`) и сравни байт-в-байт, затем прогони приёмку на реальном входе. Платформа иногда «съедает» сохранение молча.
- **ЛОВУШКА ВИДИМОСТИ (23.07, живой прогон):** global-эксперт видим на исполнение НЕ всем каналам аккаунта. REST-save с `X-Agent-Id: A` → REST-run работает, а MCP-клиент и агентский рантайм отвечают «Expert not found»; save через MCP-мост → виден MCP-клиенту, но НЕ агентскому рантайму; и только save с `X-Agent-Id: <id агента-вызывателя>` делает эксперта видимым инструментам ЭТОГО агента (проверено на `connector_execute` + `agent_XwZBKvd8dD70jKvW4WrZm`). Правило: эксперта, которого должен звать агент, сохраняй под заголовком этого агента и проверяй приёмкой через `run_agent`, а не только REST.
- **Платформа отбрасывает falsy-параметры** (False, "", 0 могут не дойти). Опасные действия защищай позитивным флагом: выполнять только при явном `apply=true`, по умолчанию dry-run.
- Global-эксперт исполняется на **случайном доступном устройстве**, если не указан target. Всё, что зависит от локального окружения (tesseract, файлы, brew), либо привязывай к target, либо переноси в локальный сервис.

### nohup-эксперты (фоновые процессы на устройстве)
- **Сырой python**: БЕЗ `$extens`/`include`/`def`/`return` сверху.
- `{{placeholder}}` подставляются ТОЛЬКО для явно переданных параметров; kwargs-дефолты НЕ подставляются → в коде обязательны фолбэки: `if not X or X.startswith("{{"): X = <default>`.
- Секреты — фолбэк из `~/extella_wizard/app/config.json`, иначе честный fail (не тихий).
- Долгую стройку/сохранение других экспертов НЕ делай изнутри device-эксперта — сохранения могут не закрепиться. Строй из внешнего клиента (мост/скрипт на хосте).

### Listener (демон на устройстве)
- Говорит с `https://disnet.extella.ai/` (НЕ api!). Пакет `extella-listener` с GitLab-PyPI, Python 3.12.
- **Новое устройство**: один раз выполнить `run_expert install_nohup_handler` + `register_cspl_shell`, иначе любой nohup/shell-эксперт падает `'str' object is not callable`. Это обязательный шаг онбординга каждого устройства/VPS.
- Listener headless: GUI-библиотек (pyobjc и т.п.) в нём нет. Всё, что трогает экран/GUI — отдельный helper в GUI-сессии.

## 6. Тулбар Extella Desktop (v6) и плагины

### Устройство
- Тулбар встроен в приложение: `app.asar → packages/extella-toolbar-suite/toolbar/build/toolbar.js` (~3 МБ, читаемый JS, 15K+ строк). Загрузчик сначала ищет **оверрайд** `~/Library/Application Support/extella-desktop/toolbar.js` — если файл есть, грузится он. Нет файла — встроенный. Это и есть механизм локальной разработки.
- Исходники (modular build): `~/extella_tools/extella-library-lite-main/toolbar/` → `src/core/*`, `src/panels/*`, `public/plugins_manager.html` (витрина) → сборка `node build.js` → `build/toolbar.js`.
- **Цикл разработки: правишь src → `node build.js` → копируешь build/toolbar.js в оверрайд → полный перезапуск Extella (Cmd+Q).** Никогда не правь build-файл руками. Каждое изменение = git-коммит (мы уже теряли source of truth — не повторяй).
- UI = плавающая пилюля: Chat | Library | Plugins. Модули `ETB.*` (auth, api, registry, plugins, marketplace…). Инъекция в BrowserView с `contextIsolation:true`, **Node/require в рантайме НЕТ** — файловые операции только через локальные серверы-мосты или экспертов.
- Витрина открывается в **blob-iframe без кук сессии** — токен передаёт родитель (это уже починено в api.js/auth.js: 401 → refresh → повтор). Помни об этом при новых iframe-фичах.

### Плагины (как добавить своё приложение в тулбар)
- Реестр: `~/extella-plugins/_registry/<id>.json`. Рабочий формат — mode `repo_ui` + `ui.local_server`: `{port, mainFile, healthPath}`; URL строится как `http://localhost:<port>/<mainFile>`.
- Конвенция автостарта: global-эксперт `_etb_srv_<plugin_id>` — тулбар зовёт его, чтобы поднять локальный сервер плагина, если тот спит.
- Локальные серверы умирают при ребуте — для постоянных используем launchd (`~/Library/LaunchAgents/ai.extella.*.plist`, живые примеры: wizard-bridge порт 8765, ta-bridge 8766).
- **Тулбар v6 не патчить ради плагина** — плагин добавляется ТОЛЬКО карточкой в реестр. Правка toolbar.js — отдельное решение владельца.
- Валидатор установки: порт брать из docker-compose/конфига приложения; **никогда не проверять :5000 и :7000** — на macOS это AirPlay (отдаёт 403 → бесконечный цикл); 2xx/3xx = живой; кап ~30 опросов.

### ⚠ KV скоупится по X-Agent-Id (23.07, чуть не потеряли каталог)
`kv/get`/`kv/set` с разными `X-Agent-Id` видят РАЗНЫЕ значения одного ключа (даже с `global: true`). Канонический скоуп витринных каталогов — заголовок `agent_extella_default` (исторический; это только скоуп-ключ, Claude не запускается). Запись «не тем» агент-заголовком уходит в теневой двойник: сначала прочитай ключ с несколькими заголовками и найди, где живёт настоящее значение (по updated_at/размеру), пиши туда же; перед перезаписью каталога — assert на минимальный размер прочитанного. Тот же класс скоупинга у ЭКСПЕРТОВ (см. §5).

### Витринные каталоги в KV
`_mkt_installed` (установленное у пользователя), `_mkt_automations` (карточки процессов), `_mkt_mcp`/`_mkt_mcp_2`/`_mkt_mcp_3` (каталог MCP-серверов; **KV шардирован** — большие каталоги режь на несколько ключей), `composer:catalog`. Аллоулист внешних MCP: `~/.extella_mcp/allowlist.json`.

## 7. Планировщик, хостинг, входящие

- Расписания: KV-ключи `sched:*` (+ `sched:__index__`). Тикер — эксперт `wz_scheduler_tick`, его надо гонять cron'ом на always-on устройстве. Сам по себе он НЕ тикает: у нас это VPS, cron каждые 15 мин. Проверяй, что тикер реально включён, прежде чем обещать «работает 24/7».
- Входящие сообщения: polling (Telegram getUpdates и т.п.), вебхуков нет. В `wz_scheduler_tick` есть ветка `reply_expert`: если в `inbound:<sid>` задан reply_expert — тик зовёт его с {message_text, chat_id, client} и отвечает его полем reply.
- Секреты клиентов — vault: шифротекст `sec:<client>:<connector>` в KV, расшифровка ЛОКАЛЬНЫМ `vault.key` на устройстве-хостинге. Ключ не покидает устройство.
- Бот на ЛИЧНОМ номере/аккаунте владельца — всегда ставь фильтр «отвечать только номерам из базы клиентов» (мы ловили инцидент, когда бот отвечал личным контактам).

## 7.5. Workspace: самонаращивание способностей (P2) — КАНОН ГЕЙТА

Движок `wz_workspace` (репо `copilot/`, плагин на порту 34767) умеет **выращивать себе новые способности из собственных тупиков**: застряла задача → `cap_design` (Qwen пишет код нового эксперта `wscap_<slug>`) → карточка-паспорт человеку → `cap_apply` по слову «разрешаю» → регистрация → диспетч по триггерам. Если правишь этот механизм — НЕ ослабляй канон:

1. **Регистрирует код только человек.** Автопилот НИКОГДА не проходит гейт `cap_apply`. Одобрение привязано к карточке (slug + sha256 кода): чужой/устаревший слаг = отказ. «Не разрешаю»/«нет» = отказ (отрицание главнее позитивной подстроки); неоднозначный ответ не закрывает вопрос.
2. **Выращенные способности v1 — ТОЛЬКО ЧТЕНИЕ.** AST-линт `_cap_lint` (не substring!): вайтлист импортов, запрет записи файлов (`open` с `w/a/x/+`), `subprocess`, голых `eval/exec/compile`, `os.getenv`, `/api/agent/*`, `/api/expert/*`. Запись файлов остаётся за отдельным гейтом записи с превью. Линт — 2-й эшелон ПОСЛЕ человека, не единственный барьер.
3. **Имя эксперта посолено `ws_id`** (`wscap_<slug>_<хеш>`) — иначе воркспейсы перезапишут код друг друга (глобальный неймспейс). Итог способности скрабится от секретов перед ledger/чатом/логом.
4. **Грабли Qwen-кодогена** (иначе `cap_design` молча пустой): слова «эксперт» в промпте быть НЕ должно (Qwen отказывается «выводить код экспертов» — защита платформы), формулируй «python-функция для личного проекта»; инструменты запретить явно (уходит в `list_rules`/`search_concepts` и ход обрывается); `max_output_tokens` ≥ 9000 (reasoning-модель ест бюджет на «мышление»); таймаут 240с и ретрай HTTP 500 (`tries=3`).
5. **Урок с прода:** человек глазами по карточке кода НЕ ловит тонкую логическую ошибку. Живой автопилот вырастил налоговую способность, считавшую ВЛОЖЕНИЯ доходом → фантомный налог $585K; поймано только прогоном. Гейт «разучиться» (`cap_forget`) — активная страховка, а не украшение. Дедуп по основам слов (`n=auto`), чтобы автопилот не плодил дубли.

## 9. Рабочая гигиена (выстраданное)

1. **Бэкап перед правкой живого файла**: `cp file file.bak_<маркер>_<дата>`. Всегда.
2. **Релиз = файл → платформа → verify → git-коммит.** Мост визарда дополнительно публикует подписанные релизы (`publish_release.py`, канал `rel:bridge:meta`, Ed25519).
3. **Перед любым push в публичный репо** — скан секретов (JWT `eyJ…`, `sk-…`, telegram `NNN:AA…`, `ghp_…`, `glpat-…`, приватные ключи) и внутренних имён/ПДн клиентов. Инфра-идентификаторы (IP VPS, target-UUID) — по решению владельца.
4. **Кириллица**: если куда-то кладёшь base64 — только `\uXXXX`-эскейпы (atob не UTF-8). В новом тулбаре base64 больше не используется, но ловушка универсальна.
5. **Не доверяй «зелёному» статусу** — прогоняй E2E на реальном входе (живой поиск, живое сообщение в Telegram) прежде чем говорить «работает».
6. Демо-данные и реальные данные клиентов держи раздельно; перед демо перезагружай демо-базу.
7. Эмбеддинг-воркер концептов периодически встаёт (новые концепты не ищутся) — есть канарейка `wz_embedding_canary`; при подозрении прогони её, а не дебажь свой код.
