# Модуль допуска для серверного приложения Extella OS: «Дать доступ» / «Отозвать»

Откуда: приложение **«Учёт клейм НацЭкс»** (Гульжан, 25.09.2026). Общие данные лежат
на одном сервере (VPS), приложение в Extella OS у каждого сотрудника ходит на этот
сервер. Вопрос «кто имеет право видеть и менять данные» решён без общего ключа в
странице и без своей регистрации: личность даёт ОС, роли — сервер, выдаёт и отзывает
доступ администратор прямо в приложении. Архитектура согласована с Codex
(`bus/collaboration/2026-09-25-shared-data-architecture.md` проекта, 3 раунда).

Файлы:

| файл | что это |
|---|---|
| `access_server.py` | сервер: `RoleStore` (roles.json / pending.json / audit.log / сессии), `whoami()` (запрос к ОС), `AccessGate` (две точки входа для http-обработчика). `python3 access_server.py --selftest` — 15 проверок + саботаж |
| `access_page.js` | страница: `ensureSession()` по `{{app_token}}`, `bridge()` для всех вызовов, `loadUsers()` — карточка администратора «Кто видит данные» |

## Как это работает (5 шагов)

1. **ОС подставляет в html страницы `{{app_token}}`** — свой у каждого, кто открыл
   приложение. В странице нет никакого постоянного ключа сервера (страж: правило
   «SERVER — только https и без ключа»).
2. **Страница шлёт `POST {SERVER}/api/session {app_token}`.** Сервер сам спрашивает у ОС
   `POST https://os.extella.ai/api/app-agent/whoami {app_token}` и получает проверенную
   личность `{user, email, agent_id, listing_id}`. Поле `user` — это **email** (замер
   25.09.2026, не 24-hex id). Сервер сверяет `listing_id` со своим — ключ другого
   приложения не проходит.
3. **Сверка с ролями.** `state/roles.json` — `{email: {name, role: user|admin, email, granted}}`.
   Есть роль → короткая сессия (случайный ключ, 8 часов) → страница ходит с заголовком
   `X-App-Session`. Нет роли → `403 {no_role:true, email}` и запись в `state/pending.json`;
   человек видит: «Доступ ещё не выдан, адрес передан администратору».
4. **Администратор в приложении** видит карточку «Кто видит данные»: ожидающие с кнопкой
   «Дать доступ» (встроенная форма с именем → `grant_user`) и допущенных с кнопкой
   «Отозвать» (двухшаговая кнопка → `revoke_user`). Себя отозвать нельзя.
5. **Роль перечитывается на каждом запросе.** Отзыв гасит действующие сессии сразу;
   удаление из `roles.json` руками — тоже. Все действия пишутся в `state/audit.log`
   (кто, что, когда; без ключей и без тел запросов).

## Встраивание в свой сервер (Python, любой http)

```python
from access_server import RoleStore, AccessGate, SESSION_HEADER, ADMIN_ONLY
st = RoleStore("/opt/myapp/state")
gate = AccessGate(st, listing_id="<listing_id вашего приложения>")

# POST /api/session
code, body = gate.open_session(data.get("app_token"))        # 200 | 401 | 403 | 502

# POST /api/call
refuse, sess = gate.check(headers.get(SESSION_HEADER), method)
if refuse: code, body = refuse                                # 401 / 403
elif method in ADMIN_ONLY: body = gate.admin(method, args, sess)
else: ...                                                     # ваша логика; sess["user"] — кто
st.audit(sess["user"], "upload", file=name)                   # журнал по делу
```

Первого администратора кладёт установка: `roles.json` с email владельца и `role: admin`.
**Установочный скрипт не имеет права перезаписать существующий roles.json** — см. класс
поломки ниже.

## Классы поломок, которые этот модуль уже ловил (и чем защищён)

| класс | что случилось | защита |
|---|---|---|
| Ключ пользователя — не тот | роли завели по 24-hex id, а `whoami` возвращает email → «нет доступа» у всех | ключ = поле `user` из whoami как есть; selftest п.4 |
| Диалоги браузера мертвы в ОС | `window.prompt` в cross-origin iframe возвращает null молча — «Дать доступ» ничего не делала | встроенная форма и двухшаговая кнопка; страж страницы запрещает prompt/confirm/alert |
| Выкладка стёрла роли | `install_remote.sh` проверял `test -f` без sudo → не увидел файл → положил «пустые» роли; два выданных доступа пропали | `sudo test -f`; страж выкладки считает роли/аудит ДО и ПОСЛЕ — стало меньше → стоп |
| Повреждённый roles.json | нечитаемый файл | = никому нет доступа, не «всем» и не падение; selftest п.7 |
| Сессия пережила отзыв | кэш роли в сессии | роль перечитывается на каждом запросе; selftest п.5 + саботаж |
| Отзыв покупки на платформе | сервер узнаёт только при новой сессии | TTL сессии 8 ч сознательно |

## Приёмка (по канону «что видит человек», не коды ответов)

1. Новый сотрудник открывает приложение → видит «Доступ ещё не выдан, адрес передан
   администратору»; у администратора он появился в списке «просит доступ».
2. Администратор нажимает «Дать доступ» → «Подтвердить» → сотрудник нажимает «Обновить
   данные» и видит данные.
3. «Отозвать» → «Точно отозвать?» → сотрудник при следующем действии получает «сессия не
   действует», данные не показываются.
4. `python3 access_server.py --selftest` зелёный; страж страницы (нет prompt/confirm/alert,
   нет ключа в странице) зелёный; страж выкладки не уменьшил роли.
