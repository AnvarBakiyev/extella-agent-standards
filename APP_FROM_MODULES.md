# Как собрать приложение из модулей

**Этот документ написан для машины.** Его читает Claude, Codex или любое приложение, которое
строит приложения из готовых узлов. Человек его не читает: он говорит, какое приложение
ему нужно, а всё остальное делаешь ты.

Владелец: Анвар (CEO Extella). Версия: 1.0, 04.09.2026 — первая редакция, проверена сборкой
одного приложения по этому тексту (§7).

---

## Слова, которые дальше встречаются постоянно

**Модуль** — это плагин, у которого наружу выведены только эксперты, а интерфейса нет.
Приложение существует для человека, модуль — для того, кто собирает приложение.
**Реестр паспортов** — это файл `capabilities_declared.json`, собранный из паспортов в git;
в нём у каждого модуля границы, требования к машине и эксперты со словами «что делает».
**Скоуп** — это набор объектов, доступных конкретному агенту; у каждого агента он свой.
**Листинг** — это карточка продукта в магазине.
**Гейт** — это машинная проверка, которая обязана уметь провалиться.
**Предрелиз** — это версия продукта в магазине, которую видит только автор.
**Пять форм** — это закрытый словарь содержимого между приложениями: список, число, шаги,
связи, документ (`КОНТРАКТ_ПЯТИ_ФОРМ.md`, код в `tools/формы.py`).

## 0. Что от тебя требуется в одном абзаце

Тебе дают задачу человеческими словами: кому нужно приложение и что оно делает. Ты
раскладываешь задачу на потребности, по каждой находишь модуль в реестре паспортов, честно
называешь дыры, пишешь план экранов в пяти формах, собираешь каталог продукта одной
командой, делаешь эксперты модулей видимыми агенту приложения, прогоняешь гейт приложения
по стадии и доводишь продукт до предрелиза. Проверялки, а не этот текст, являются
спецификацией: `tools/check_app_from_modules.py` знает больше, чем написано ниже.

Стадию объявляй первой (§0а `AGENT_BUILD_GUIDE.md`): на стройке модуль без паспорта даёт
предупреждение с именем, на проде — отказ.

---

## 1. Что такое приложение из модулей и чем оно не является

Приложение из модулей — это страничный продукт магазина: одно окно, собранное из пяти
форм, и агент приложения, в скоупе которого видны эксперты выбранных модулей. Окно зовёт
эксперт через `app-agent/run`, эксперт исполняется на компьютере покупателя, ответ ложится
в одну из пяти форм и рисуется в окне. Кода у приложения нет, кроме одного эксперта
состояния, который собирает сборщик.

Чем оно не является:

- не чат: сотрудник видит очередь, поля и кнопки, а не диалог;
- не новый сервер: у приложения нет порта и процесса, всё живое исполняют эксперты модулей;
- не копия модулей: эксперты модулей глобальные и остаются одни на всех приложениях.

Почему так: интерфейс меняется чаще способности, а восемь продуктов с восемью серверами дали
почти весь журнал поломок августа. Приложение из модулей повторяет тонкий режим каркаса
`new_product.py`, только вместо таблицы маршрутов у него реестр.

## 2. Что нужно до начала

1. **Реестр паспортов пересобран** на этой машине и опубликован для устройств:

```
python3 tools/build_capability_registry.py --roots-file config_registry_roots.txt \
    -o ~/extella_wizard/registry/capabilities_declared.json --publish
```

2. **Агент приложения существует.** Окну модель не нужна, только запуск экспертов, поэтому
   агента можно создать по API (канон платформы, правило 6). Основной агент
   `agent_extella_default` и агенты чужих продуктов целью быть не могут: чужое живое не
   трогать.
3. **Слушатель Extella поднят** на машине, где будет проба: без него эксперт модуля исполнится
   не там, где лежат файлы, и ответит «файла нет».
4. Токен платформы лежит в `~/.extella/api_token.txt` или в конфиге моста.

## 3. Разложить задачу и найти модули

Составное задание целиком не ищется: правило поиска требует половину слов задачи или
подтверждения семантики, а пять потребностей в одном предложении не закрывает ни один
модуль (замер 04.09.2026: на брифе из пяти потребностей поиск отдал три способности и ни
одного модуля распознавания, на подзадаче про счета модуль пришёл первым). Поэтому:

1. Разложи задачу на потребности, по одной фразе каждая: «распознавать счета из сканов»,
   «вести контрагентов и сделки», «отправлять документ в 1С».
2. По каждой спроси реестр: `run_expert wz_capability_find` с `task` из одной потребности.
   Бери только ответы с `declared: true` — у них известны границы (`limits`) и требования
   к машине (`needs`). Ответ с `declared: false` — это способность без паспорта: на стройке
   её можно взять с флагом `--без-паспорта`, на проде нельзя.
3. Потребность без модуля запиши словами в план (`missing_ru`, `missing_en`) и в блок «чего
   не обещаем» окна. Приложение, которое молчит о дыре, хуже приложения с дырой.

Граница модуля решает, что окно обещает. Модуль распознавания отдаёт текст, а не поля
счёта — значит экран «реквизиты» без модуля разбора не собирается, и это пишется в план.

## 4. План приложения `app.json`

Образец: `python3 tools/окно_из_форм.py --пример`. Правила, которые проверяет
`проверить_план`:

- `slug`, `name` и `description` на двух языках, `agent_id` вида `agent_…`, `modules` —
  идентификаторы из реестра;
- каждый экран — одна форма из пяти и ровно одно из двух: `static` (готовое содержимое) или
  `action` (кнопка). У кнопки: эксперт, поля ввода, текст ожидания на двух языках и `map` —
  как ответ эксперта ложится в форму: шаблоны вида `{text}` берут поля из ответа, списочные
  формы берут массив по ключу `from`;
- главное действие на экране ровно одно — поэтому у экрана одна кнопка;
- `help` на двух языках: шаги, что гарантировано, **чего не обещаем** (обязательно), кто
  может раскрыть или откатить. Без блока «чего не обещаем» окно не собирается (§3.20).

Эксперт кнопки обязан принадлежать модулю из `modules` или самому приложению — гейт
отвергает чужой эксперт, потому что для него нет ни паспорта, ни провижининга.

## 5. Собрать, провести, проверить

```
python3 tools/build_app_from_modules.py apps/<slug>            # каталог продукта из плана
python3 tools/provision_modules.py apps/<slug>                  # эксперты видны агенту приложения
python3 tools/check_app_from_modules.py apps/<slug> --stage build
```

Что делает сборка и почему это не пишется руками:

| Файл | Откуда берётся |
|---|---|
| `index.html` | окно из плана: пять форм, кнопка «? Как это работает», живой вызов, видимое ожидание |
| `listing.json` | имя, описание, теги, права `expert.run` и `device.run`, границы модулей |
| `MANIFEST.yaml` | объединение манифестов модулей, одна проверка на зависимость |
| `manifest_check.py` | копия канона байт в байт |
| `docs/automation_passport.yaml` | паспорт приложения: агент, эксперты модулей с «что делает», границы, откат |
| `experts/<slug>_state.py` | состояние по схеме `extella.automation_state.v1`, неизвестное — `null` |
| `icon.png` | канонический генератор `bronze_icon.py` |

Провижининг делает эксперты видимыми агенту приложения и ничего больше. Четыре правила,
каждое куплено поломкой:

1. `instructions` агента не пишутся никогда: у любой копии агента там ядро платформы на сто
   девять тысяч знаков, и `agent_forge` его стирал.
2. Глобальный эксперт, который агенту уже виден, не копируется: одно имя в двух скоупах даёт
   недетерминированный запуск.
3. Копия делается только для невидимого, под заголовком агента приложения, и тут же
   перечитывается: «успешно» от платформы фактом не является.
4. Отчёт `provisioning.json` кладётся рядом с планом; гейт читает его, а не верит словам.

Гейт приложения зовёт существующие проверялки (паспорт, права, ожидание, бренд) и добавляет
только то, что есть у приложения из модулей: реестр, план, провижининг. Его сообщения на
двух языках; коды начинаются с `APP_`.

## 6. Довести до предрелиза

Приложение из модулей — страничный продукт со своим агентом. Агент прикрепляется к листингу
только при создании: `publish-stream` с полями `source_id`, `source_type=agent`,
`attach_agent=1`; добавить агента к уже созданному листингу нельзя (замер 25.08.2026, ответ
`403 this app has no deployed agent`). Обычная выкладка страниц этого не делает, поэтому у
приложения из модулей свой инструмент:

```
python3 tools/deploy_app_from_modules.py apps/<slug>                 # план, без записи
python3 tools/deploy_app_from_modules.py apps/<slug> --выполнить     # предрелиз и приёмка чтением
```

Приёмка читает обратно: листинг не опубликован, права и агент версии совпадают с планом,
эксперты читаются из скоупа агента, страница отдаётся с подставленным `app_token`, без
токена аккаунта и с кнопкой «? Как это работает». Права `expert.run` и `device.run`
объявляются при создании: без второго `targets` вырезается, и эксперт исполнится в
контейнере, где файлов покупателя нет.

Покупка себе — флаг `--купить-себе` (`purchase-stream` с `deploy_mode=existing` и
`target_agent_id`): после неё листинг нельзя удалить, поэтому это отдельное решение.
Дальше — по `README.md` «Как довести до магазина»: первый запуск чистым состоянием, сценарий
живьём, остановка. Кнопку «Publish» жмёт человек.

## 7. Замер: сколько часов у создателя

Метрика квартала — человеко-часы на развёртывание. Для приложения из модулей она считается
у создателя, а не у Extella: запиши время от первой строки плана до зелёного гейта и до
предрелиза в отчёт сборки (`apps/<slug>/README.md`, строка «Собрано за»). Первый замер —
04.09.2026, приложение «Чтение счетов» из одного модуля: см. `gtm/moduli-den-1.md` в мосте.

## 8. Чего стандарт сознательно не требует

- Своего сервера, порта и процесса у приложения: если потребность требует процесса, это
  модуль класса «сервис», и он живёт в библиотеке модулей, а не в приложении.
- Второго словаря содержимого: формы пять, новая добавляется решением владельца.
- Агента с моделью: окну хватает запуска экспертов. Нужен диалог — это отдельное решение и
  отдельный агент, созданный человеком в интерфейсе.
- Копий экспертов модулей в каждом приложении: модули общие по определению.
