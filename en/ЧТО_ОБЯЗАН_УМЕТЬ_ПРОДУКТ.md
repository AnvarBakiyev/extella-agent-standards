# What an Extella product must be able to do

One page for builder chats. Every item comes from an actual breakage; the cost is
given. Details and measurements are in `DEPLOY_REQUIREMENTS.md`; rule numbers appear
in parentheses.

## 1. Always open — even when everything is broken

**An empty or white window is a defect, not "still loading."** It is not caught by
code review or by tests: the failure happens on the first access to an incomplete
snapshot of data.

- **A splash screen from the first frame.** While there is no data yet, the person
  sees not a bare shell, but "Opening your cabinet" with words about what is
  happening.
- **A snapshot is always assumed incomplete.** The panel comes up before device
  confirmation; the first response arrives without settings — the code must survive
  that.
- **Built-in data is mandatory.** No connection — we open on a demo slice with an
  honest caption "training database · your own 1C is not connected". **Absence of
  connection is a state, not a refusal.** The demo slice covers ALL blocks of the
  screen: one empty block next to filled ones reads as a breakage of half the
  product.
- The OS window **must not be reloaded from the page** — `reload` on a 401 kills it
  for good. The window's origin is `null`: a direct external `fetch` gives "Failed to
  fetch" with no explanation. (H101)

## 2. Do not lie with numbers

**Zero is the statement "there is nothing here," not "I don't know."** The screen
showed a debt of 16.5 million and four zero baskets by age plus the caption "over 90
days — none." The calculation was correct, but the statement was a lie: there was
nowhere to get the age from. An accountant who believed it would not go and sort out
the overdue debt.

Didn't calculate it — state the amount and **the reason in words**, remove the empty
breakdowns, do not phrase a negation about something you did not check. Test for a
new screen: what will it show if the client is missing the required field. The
answer "zeros" — redo it. (H99)

## 3. State the reason for a refusal

The form of any refusal: **what happened → why → what to do**. A person never sees
the error code; the code goes into the log.

> The computer with 1C is not responding right now. Wake up the Windows computer and
> check that Extella is running on it (Start), then try again.

Separately, the practice of "the screen states what it cannot cross-check" reduces
anxiety: "the counterparty's BIN is not filled in — cannot cross-check" instead of a
silent guess. (H101)

## 4. Install on someone else's machine

- **`install.py` strictly at the ROOT of the archive.** One level deeper and the
  platform will not find it.
- **One installation root.** Right now storefront products put files in three
  different places (`~/.extella/`, `~/extella-apps/`, `~/extella_apps/`) — with this
  inconsistency neither an audit nor removal is possible. Use `~/.extella/<app>/`.
- **No tying to a single OS.** `launchctl` without branches — the product installs
  only on a Mac, and for three months nobody notices, because all the authors are on
  Macs.
- **Autostart does not decide install success.** No way to register the service —
  the files are still laid out, the server is still brought up, and the manual
  command is still printed.
- **Port:** if taken — take the next free one; check that the service on the port is
  **ours** (the app name in `/health`), otherwise an impostor will be accepted as our
  own. (H98, H103)
- Run `tools/check_installable.py` **before** publishing.

## 5. Be fast where it is actually slow

The main source of delay is usually the **route**, not rendering: 46–59 s versus 13 s
after the window started trying the local path first. A 1.78 MB page was not the
problem — the seconds lived in the network.

If the product can work locally — the local path goes first, and the result is
visible to the person ("1C is connected · directly"). A dead route **is remembered**
and is not tried on every call; a fresh port is not re-queried; bootstrap is not
requested twice at startup. (H100)

## 6. Roll out reproducibly

- **A full test run**, not "affected ones": half the defects are found in files
  nobody touched.
- **Cross-check fingerprints** — print "the archive and the installer carry
  `<хеш>`", otherwise the store ends up with something other than what was built.
- **Do not touch the sources during the run** — the build will drift apart from the
  code.
- Publishing a version sometimes fails with a timeout (retry until confirmed);
  deleting the previous version returns **409** if someone still has it installed.
  (H102)

## 7. Know other people's rakes, so as not to step on them again

- **A built page is a template.** Opened as a file, it fails and **silently falls
  back to demo data**: the author was recording a video thinking they were working
  with the live database.
- **A trailing end-of-line comment eats the code after it** — the syntax is intact,
  the tests are green, the screen stays silent.
- **A new file that was not added to the delivery list** works for the author and
  fails for the client.
- **An "optional" field of an external service** can be mandatory in prod.
- **Check with the final action:** 1C accepts the document for writing and then
  refuses to post it.
- **Windows:** `CREATE_NO_WINDOW` (`0x08000000`, not `0x00000008`) together with
  `DETACHED_PROCESS`, otherwise the user gets black windows; `CREATE_BREAKAWAY_FROM_JOB`
  (`0x01000000`) — otherwise the process dies together with its parent. Printing
  Russian text without `reconfigure(encoding="utf-8")` crashes the installer on
  `charmap`. (H103)

## 8. Device diagnostics: two platform responses

- **HTTP 500 `Target … is unavailable`** — the device does not exist or is not
  reachable.
- **HTTP 200 + a syntax error on the first line of the container** — the device **is
  alive**, but in **someone else's account**. The error text drifts between runs of
  the same code — syntax does not behave like that.

An empty `targets/list` proves nothing: the list is scoped per agent. Check with a
probe that has explicit `targets`. (H104)

---

## Acceptance conditions

The product is ready when everything below holds on a **clean machine**:

1. the storefront button carries the install through to the end and states so
   honestly;
2. files have appeared in the declared root;
3. the shortcut is placed on the Desktop, and it opens the window;
4. **the app is visible in the window** — not a shell, not a white screen;
5. when a dependency is missing (Docker, 1C, network) the window **states the
   reason and the next step**;
6. no screen shows a calculated value where there was nothing to calculate from.
