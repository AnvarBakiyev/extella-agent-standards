# H28. THE REQUEST LIMIT IS SHARED PER MACHINE, AND THE PANEL MUST NAME THE REFUSAL

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H28. THE REQUEST LIMIT IS SHARED PER MACHINE, AND THE PANEL MUST NAME THE REFUSAL

**Found by the Recruiter panel chat on 17 Aug 2026.** A person pressed the button twice,
the panel answered "The app didn't respond." The limit is counted **per IP address**, and
in that same minute four others were firing from the same machine: the hourly task agent,
deploy-time checks, the installer, and the panel itself.

**1. The request budget is shared per machine, not per product.** Anything running on a
timer must yield to a live person: spread its calls over time, back off on a refusal,
never hammer with retries. Automation that eats up a client's minute is a defect, not
background noise.

**2. The panel has no right to turn every refusal into "didn't respond."** The named
reason is part of the product: "rate limit, wait a minute," "no permission," "the service
is stopped." One phrase for every case is the same silent refusal, just a polite one: the
person doesn't know what to do and repeats the click, finishing off the limit.

**Probe of 17 Aug 2026: there's no way to learn the remaining quota.** Neither on a
successful core response nor on a refusal is there a single header about the limit — no
`X-RateLimit-Remaining`, no `Retry-After`. A request to the platform: send these, and
return `429` with a body instead of `500`.

**The real cause of that incident turned out to be something else** (and this is a
separate lesson): the interface passed five arguments to the method, the method accepted
four. The limit was a coincidence, and "didn't respond" hid both problems. The
`check_ui_api_contract` gate now checks the argument count.
