# H30. A SECRET FOR AN EXPERT: where it lives and how it's read. Measured from the inside

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H30. A SECRET FOR AN EXPERT: where it lives and how it's read. Measured from the inside

**A colleague's question, 17 Aug 2026:** the expert needs a third-party service key, and
through MCP `get_kv` the value arrives as `$enc:IV:base64`, while a direct POST from the
expert answers `401 Authentication required (user_id missing)`. Verified with a scout on
the device.

**1. There is NO standard function for reading a secret in the expert's runtime.** Of the
expected names (`get_kv`, `get_secret`, `kv`, `extella`, `platform`, `mcp_call`), exactly
one is available: `include`.

**2. `$enc:` is how it looks from MCP's side, not a storage method.** The same key over
REST with three headers arrives as **plain text** (probe: 30 characters, no prefix).
There's nothing to decrypt — it needs to be read a different way. `~/.extella/vault.key`
plays no part in this: the file isn't on the machine at all.

**3. The listener PLACES the token in the expert process's environment** —
`EXTELLA_API_TOKEN` (36 characters). Next to it: `EXTELLA_BRIDGE_SECRET`,
`EXTELLA_BRIDGE_ACCOUNT_BINDING`, `EXTELLA_BRIDGE_PORT` — not needed for KV. Hence the
reason for the 401: there were no headers at all. With the token but without an agent —
`422`, the `x-agent-id` field is required. **Three headers → 200.**

**4. `X-Agent-Id` does NOT arrive in the environment, and that is not a minor detail.**
KV lives within the agent's scope: the same key with a different id gives **`500 Key not
found`** (probed), not an empty response. So the expert must receive the agent id as a
PARAMETER; taking it from `~/extella_wizard/app/config.json` is unsafe — a different
agent may be set there, and you'll get "key not found" on a key that exists.

**5. No convention of `api_key_name="…"` with automatic key substitution was found**,
either in the runtime or in parameter behavior. Don't expect it; the CTO is building
closed KV with input through the OS interface separately.

**6. A recipe, verified against a live key:**

```python
$extens("include.py")
def мой_эксперт(агент="", ключ="qwen_api_key"):
    include("import requests", ["extella-pip install requests"])
    import json, os
    токен = os.environ.get("EXTELLA_API_TOKEN", "")
    if not токен or not агент:
        return json.dumps({"ошибка": "нужен параметр агента; токен даёт листенер"},
                          ensure_ascii=False)
    о = requests.post("https://api.extella.ai/api/kv/get", json={"key": ключ},
                      headers={"X-Auth-Token": токен, "X-Profile-Id": "default",
                               "X-Agent-Id": агент}, timeout=60)
    if о.status_code != 200:
        # 500 «Key not found» = ключа нет В ЭТОМ скоупе, а не поломка платформы
        return json.dumps({"ошибка": f"KV ответил {о.status_code}"}, ensure_ascii=False)
    секрет = о.json()["value"]      # открытый текст: в ответ и в журнал не кладём
```

**The secret is not printed anywhere** — the expert's response is seen by the chat, and
the chat is seen by the person.

**7. For a buyer from the store**, the key is set by that person themselves, in their own
KV and within their own agent's scope. A page-type product goes through a different path:
`app_token` + the `kv.read` permission via `app-agent/run`, where the agent is implied by
the purchase. A sold copy's owner's key is not accessible to someone else — as it should
be.

**AMENDMENT, 17 Aug 2026, same day: the token may be MISSING from the environment.**
Probed on two machines:

| machine | what's in the expert's environment |
|---|---|
| the owner's Mac | `EXTELLA_API_TOKEN` (36 characters) + bridge variables |
| the colleague's machine | **only `EXTELLA_API_URL`**, no token via either `run_expert` or `run_agent` |

So the injection depends on the machine or the listener version, and the "token from the
environment" recipe is not universal. I gave it out as universal — that was a mistake
that cost the colleague a debugging cycle.

**The order is now this, not the other way around:**

1. **the primary path is a file next to the product** (`~/extella_wizard/app/<name>.key`,
   mode 600) with an honest refusal if the file is missing. Works in any context, on any
   machine;
2. **the environment is a nice bonus**: if `EXTELLA_API_TOKEN` is present, read the
   agent's KV and get a key tied to the account, not to the machine;
3. **never treat a missing token as a platform failure** — it's a difference in the
   launch context. The refusal must name what's missing, not say "didn't work."

**What we recommend.** Our own perimeter — the agent's KV. Someone else's machine — a
file next to the product with an honest refusal if the file is missing. From the
listener's environment, only `EXTELLA_API_TOKEN` can be relied on.
