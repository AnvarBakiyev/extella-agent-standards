# H45. STOREFRONT RECONCILIATION: check the artifact through the buyer's eyes, not the author's

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H45. STOREFRONT RECONCILIATION: check the artifact through the buyer's eyes, not the author's

**Log of the "1C Agent" chat, 20–21 Aug 2026. The clean-install test stand confirmed this
class of bug live: version 1.11.1 did not install for a single buyer, caught before the
very first one.**

The root cause. A listing version's snapshot **freezes the archive** at `add-version`,
but the buyer gets experts from the LIVE source agent. Any refresh of the source after the
version was cut drives the pair apart: a clean buyer gets an honest refusal
`release_mismatch: the archive carries release X, while the installer is flashed with Y`.
On the team's own machines this is invisible — local release directories paper over any
checksum mismatch.

Two rules follow from this:

1. **Roll out in a single pass:** flash → source → archive → version. Don't refresh the
   source before the next release.
2. **Storefront reconciliation — a technique adopted into the canon.** After a rollout,
   check the artifact the way the BUYER sees it: download the archive FROM THE STOREFRONT
   the same way the installer downloads it (`/api/app-archive`), pull the release
   fingerprint, and compare it against the expert flash read from the LIVE source via
   `expert/get`. Checking your own build on your own machine does NOT count — the
   author's environment masks exactly the class of bug that kills a clean install. The
   reconciliation is built into the version-creation script
   (`os_app/add_os_version.py::storefront_consistency_check`) and blocks closing out the
   rollout on a mismatch.

This is the same principle as the `tools/bench/` test stand: the proof is not "green for
the author," it's "works for the buyer on a clean machine."
