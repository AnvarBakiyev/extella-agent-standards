# H106. THE OS PAGE CALLS THE EXPERT VIA APP_TOKEN, NOT VIA THE TOOLBAR BRIDGE

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H106. THE OS PAGE CALLS THE EXPERT VIA APP_TOKEN, NOT VIA THE TOOLBAR BRIDGE

**Live measurement, 22 Sep 2026, in an actual Extella OS window through the debug port** (by two
executors independently: the canon keeper and the Codex chat). In
`desktop.*.js` there is no handler for `etb_run_expert`; `etb_init` only carries
`{theme, lang}`; the page's frame has `origin: null`, so any reference to
`parent.extellaDesktop` ends in a `SecurityError`. The `etb_*` protocol belonged to the
toolbar that was removed on 12 Aug. A page built on it looks intact, but its buttons
cannot call the expert.

**The working contract (cross-checked with the 1C Agent and the Recruiter):**

1. Declare `{{app_token}}` in `index.html`. Do not request the full `{{token}}`.
2. Make all calls as `POST https://os.extella.ai/api/app-agent/run` with the body
   `{app_token, expert_name, params, targets?}`. No messages to the parent window and
   no reading of its JavaScript API.
3. Send the first call to the dispatcher expert **without `targets`**. From the response take
   `pageRoute.targetId`; the fallback is `device`/`device_id` in the transport envelope.
4. Send all subsequent calls with `targets: [the device received]`. If the first response
   contains no device, show the person the specific reason and leave the retry available.
5. Request the `expert.run` and `device.run` permissions. Respect the channel limits:
   30 calls per 60 seconds, body up to 64 KB, app-token TTL of two hours (refreshed by
   reloading the window), a synchronous terminal response per H54.

**A temporary workaround for §46 until the platform fixes device selection.** If the first
call without `targets` returned `[Execution Error] ... (<container>, line 1)`, that's the
signature of H104: the platform picked a computer whose listener is signed into another
account. The app must explain this in words, show a Device ID field and a "Work through
this device" button, then check the dispatcher with an explicit `targets: [device_id]`.
The Device ID is kept only in the open window's memory: `localStorage` throws
`SecurityError` in the sandbox, so on the next opening the person enters it again. Do not
show the field for other errors. This path was adopted in the live 1C Agent window 1.66.0
and re-verified with the H106 pre-release on 22 Sep 2026.

**Machine guard.** The `tools/new_product.py --thin` generator and the
`templates/app-recipe` recipe must contain `{{app_token}}` and `app-agent/run`, and the
generated page must not contain `etb_run_expert` or `parent.extellaDesktop`. The gate
must reference rule number `H106`, otherwise the rule isn't considered covered.

**Acceptance.** Only a real OS window: closed pre-release → desktop shortcut → the first
call returned the id of an open device → the second call with that id returned the same
machine's name. A stand simulation and a direct HTTP request are useful before release,
but they don't replace this acceptance.

**Measurement from inside the window's frame:**

| What was checked | Result |
|---|---|
| `etb_init` from the OS | only `{theme, lang}` — no device |
| the `etb_run_expert` handler in the OS build (`desktop.*.js`) | **0 mentions** — the call goes nowhere |
| `getDeviceID` in the OS build | 0 mentions |
| the app window's frame | sandboxed, `origin = null` |
| `parent.extellaDesktop` from the frame | **SecurityError** — the browser blocks it |
| the OS desktop itself | `extellaDesktop.getDeviceID()` exists and returns a UUID — but is not reachable from the app window |

**The first call without `targets` — where it goes.** Measurement on 22 Sep in a probe
window (listing `40cf6ccf…`, expert `h106probe_where`, the same `app_token`):

| `targets` | result |
|---|---|
| none | `invalid decimal literal (<container>, line 1)` |
| `39f81469…` ("Windows with 1C," listener signed into another account) | the same error, verbatim |
| `85800354…` (VPS) | success, `host: extella-team` |
| `24f37e45…` (Mac) | success, `host: Anvars-MacBook-Pro.local` |

This is the signature of H104 — a computer from someone else's account, not a cloud
runtime: the account's own code would have run in the cloud. The platform sends the call
without pinning it to a machine where it cannot be executed (CTO letter, §46). The recipe's
bridge turns this signature into a reason stated in words; "Extella did not report the
device, restart" is wrong here.

**A correction to my own mistake.** On the morning of 22 Sep the canon keeper wrote here
"a second path — `parent.extellaDesktop.getDeviceID()`," having checked it on a
simulation stand. In a live window that path is closed by the sandbox. The lesson is the
same as H104: **a simulation stand proves the logic but not the environment** — a rule
about the environment is only accepted after a probe in a real window.

**Verified in a live window** (the recipe's bridge embedded in a real frame, the real
platform): device known → success in 9.5 s, the call is pinned; device unknown → the
reason stated in words; a remembered device disappeared → forgotten, one retry. Guard:
`templates/app-recipe/tools/check.py` (comments don't count, permissions, experts present
in the delivery) and `tools/new_product.py --selftest`.
