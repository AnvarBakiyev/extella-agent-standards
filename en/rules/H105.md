# H105. JAVA WINDOWS (NCALayer) ARE DRIVEN BY KEYBOARD, NOT MOUSE. THE PASSWORD ONLY AFTER CHECKING THE WINDOW

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H105. JAVA WINDOWS (NCALayer) ARE DRIVEN BY KEYBOARD, NOT MOUSE. THE PASSWORD ONLY AFTER CHECKING THE WINDOW

**Where this rule comes from — matters for trust.** A colleague did the measurements on her own
machine, the 1C Agent chat gave the explanation, **the canon keeper did not reproduce it**. The 1C
chat explicitly noted that it never touched the window with its own hands: in the 1C Agent it took
a different path — through the **NCALayer protocol**, not through the interface. Confirm the
points below on your own machine before adopting them.

**Measurement (colleague).** The NCALayer 1.4 window is drawn in Java (Swing). Such a window has
**one real Windows window** — the frame; the buttons and fields inside are drawn by Java on a
canvas, and as far as the system is concerned they don't exist. From this, three observations:

* clicking on the button's coordinates **misses** — the coordinates come from something that
  doesn't exist in the system, and at 150% screen scaling the logical coordinates diverge from the
  physical ones by half again;
* invoking the UI Automation `invoke` pattern **returns success and does nothing** — the system
  hands back a stub that formally has the pattern;
* **`Enter` after `set_focus` works** — the keyboard is the only channel that honestly crosses the
  Java boundary: the keypress goes into the window, and from there Java's own focus system handles
  it.

**Cost.** Empty signatures with no error message: the automation "succeeded," the document is not
signed. A silent success is the most expensive kind of refusal — no green test catches it.

**Rule:**

1. **Drive with the keyboard.** Find the top-level window, set focus, then only `Tab`, arrow keys,
   space, `Enter`. No coordinates and no UI Automation patterns.
2. **Wait for the window, don't assume it.** Java windows appear before they are ready to accept
   input: wait for a stable sign → pause → focus → **confirm the window is frontmost** → only then
   keystrokes.
3. **Branch on the window, not on the scenario.** NCALayer has two kinds of window (the long one
   with the password, and the short "Sign" one) — there can be no fixed sequence of keystrokes. The
   distinguishing sign (title, class, size) **must be measured on your own setup**, it's
   version-dependent.
4. **The process declares itself DPI-aware**, otherwise both the coordinates and the "did we hit
   the window" checks lie.

**THE UNCONDITIONAL REQUIREMENT ABOUT THE PASSWORD — not an option.** Focus in Windows can be
stolen by anything: a notification, an antivirus, another program, the person themselves. If at
that moment the robot is typing the digital-signature password, the password goes **into whatever
window turned out to be frontmost** — a chat, a document, a search field — and stays there in the
history.

Therefore **immediately before entering the password, re-fetch the handle of the frontmost window
and compare it against the target; if it doesn't match, abort and type nothing.** This check is
mandatory and must not be disabled.

**And the architectural conclusion, worth more than all four points above:** if the external
program has a **protocol**, work through the protocol, not through its window. The 1C Agent did
exactly that and got none of these breakages. Automating someone else's interface is a last resort,
and for signing a document it's best avoided entirely: the signature is placed by a person.
