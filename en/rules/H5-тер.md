# H5-ter. The purchase mode decides whether the agent will be new — and it is easy to miss

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H5-ter. The purchase mode decides whether the agent will be new — and it is easy to miss

Observation from a probe: after reinstalling, the page got a different `agent_id`
(`agent_x8qw…` → `agent_3UNL…`), and the call failed with `Expert not found` — the
expert had stayed in the scope of the previous agent.

**Amendment, 12 Aug 2026 (the owner).** This is not an automatic reinstall behavior: the
purchase asks for a mode — deploy a **new** agent or install **into an existing one**
(`deploy_mode: new | existing` + `target_agent_id` in the API). The new agent appeared
because the "use existing" button was not pressed. In other words, the cause is a
**choice of mode, not an inevitability** — but this choice is made in passing, and its
consequences are quiet.

* **The product's scope does not survive an agent change.** The experts laid down by the
  installer will arrive again by themselves; but everything a person or a chat put into
  the scope AFTER install — rules, concepts, custom settings — will stay with the
  previous agent. From the outside this looks like "the product suddenly forgot its
  settings."
* **Check `agent_id` after every reinstall**: if it changed, a new agent was deployed, and
  everything customized stayed with the old one.
* **Agents multiply:** one listing, over three reinstalls, produced three agents.
* So store product settings somewhere an agent change won't lose them (a KV with an
  explicit product key, a file on the device), not "in the scope, because it's
  convenient."
