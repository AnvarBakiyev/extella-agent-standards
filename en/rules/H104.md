# H104. HOW TO TELL A DEAD DEVICE FROM SOMEONE ELSE'S: TWO PLATFORM RESPONSES

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H104. HOW TO TELL A DEAD DEVICE FROM SOMEONE ELSE'S: TWO PLATFORM RESPONSES

**CAUSE FOUND ON 24 Sep 2026 — IT'S THE KEY, NOT THE ACCOUNT.** The listener decrypts the expert's
code with a key derived from the device's PIN: in `extella_listener/listener.py` the key is computed
as `sha1(PIN)` and passed as the `--crypto-key` parameter. If the key is wrong, undecrypted garbage
arrives on the device, and Python reports it as a **syntax error on the container's first line**.

The probe that proves this (one line, reproducible by anyone): run any working expert on **your
own, healthy** machine, passing a deliberately wrong `pin`.

| call on `24f37e45…` (the owner's Mac, answered a second ago) | result |
|---|---|
| without `pin` | `{'status': 'success', 'host': 'Anvars-MacBook-Pro.local'}` |
| `pin: "0000"` (wrong) | `[Execution Error] invalid decimal literal (<container>, line 1)` |

**Hence the correct wording of the symptom:** the error means "**the code failed to decrypt on the
device**." Someone else's account is only one of the causes (there the listener runs with a
different PIN); the others are: a wrong `pin` passed in the call, the listener started with a
different `--crypto-key`, the device was re-registered while the key stayed the same.

**What to check, in order:** the call's key (was `pin` passed, and is it the right one), the
listener's key (which `--crypto-key` it was started with), and only then the account. The earlier
edition below is factually correct but named the account as the cause — read it with this
correction.


**Control measurement, 21 Sep 2026.** The same four-line probe sent with an explicit
`targets=[device_id]` to three devices:

| device | response |
|---|---|
| removed the day before | **HTTP 500** `{"message": "Target … is unavailable"}` |
| a fully made-up id | **HTTP 500** `{"message": "Target … is unavailable"}` |
| alive, but on someone else's account | **HTTP 200** + `[Execution Error] invalid decimal literal (<container>, line 1)` |

**Rule — a distinguisher that saves a day:**

* **HTTP 500 "Target … is unavailable"** — the device doesn't exist, was deleted, or is not
  connected.
* **HTTP 200 with a syntax error on the container's first line** — the device is **alive and
  answering**, but belongs to another account: the job arrives, the expert's code arrives
  undecrypted. The error text itself **drifts** between runs of the same code (`invalid decimal
  literal`, `cannot assign to expression`, `invalid syntax`, `leading zeros…`) — syntax doesn't
  behave that way.

**Cost, paid twice.** On this signature the Schemes Board chat lost hours, and the canon keeper —
two days and a deleted server: they went through Cyrillic in identifiers, expert format, listener
version with SHA-256 package cross-checking, listener count, encryption key, device
re-registration — on a perfectly healthy machine.

**What NOT to do with an empty `targets/list`.** An empty `results` is not a sign that the record
doesn't exist: the list is **scoped** by agent. Measurement, 20 Sep 2026: `/api/targets/list` with
`X-Agent-Id` returned `results: []` on an account where a search by account showed five live
targets in the same minute. Check with a probe that has explicit `targets`, not with the list.

**There is no standard way to move the listener to another account** (verified 17 Sep and 21 Sep):
signing into the app window doesn't move the listener with it — it authenticates with its own token
separately. The working path is to work from the account where the listener lives. Changing
`device_id` isn't free: the store pins the app to the device of first install ([[§45]]).
