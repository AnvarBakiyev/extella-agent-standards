# H115. REPOSITORY RAILS: FOUR CHECKS BEFORE THE COMMIT, NOT A CONVERSATION AFTER

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H115. REPOSITORY RAILS: FOUR CHECKS BEFORE THE COMMIT, NOT A CONVERSATION AFTER

**An audit of four staff members, 25 Sep 2026, 14 repositories, about 14,000 lines.** The same
result for everyone: in a repository with a written standard, a person works by the standard;
without a standard, they hand in a working but unprotected prototype. The cost was measured:

| what was found | where | cost |
|---|---|---|
| a full database-access key in a public repository since 8 Jul, valid until 2036 | a product for farmers | phone numbers, land plots, contracts; access codes hashed without salt |
| the names and birth dates of 19 employees in a public repository | a greeting bot | the bot itself appends data on every command |
| anonymous access to our paid keys with no authorization | a demo agent | our model bill and the client's documents open to the world |
| a Python syntax error in production | an analytics backend | 3 commits out of 5 — fixing one bracket over 13 hours |

**Rule. A repository is considered set up once it has rails in place**
(`templates/repo-starter/pre-commit`, installed with one command):

1. **Syntax** — `py_compile`, `node --check`, parsing JSON before commit.
2. **Secrets by shape, not by variable name** — JWTs, provider keys, bot tokens.
3. **Personal data — by TWO independent signals** (birth dates with actual values, distinct phone
   numbers, emails, national ID numbers), not by one.
4. **Build junk** — caches and compiled files.

**Plus three conditions that can't be enforced by a machine:** the repository is private by
default; the key lives in an environment variable and nowhere else; everything that ships to the
buyer goes through someone else's review.

**A refusal is bypassed knowingly** (`--no-verify`) and names what and where: a ban that can't be
bypassed gets bypassed entirely (the same argument as the designer's point in the design gate).

**Measurement, 26 Sep 2026: a live commit found three flaws in the rails themselves, invisible to
the self-check.** This is the same lesson as H114, but now about our own guard:

| flaw | how it looked | why the self-check stayed silent |
|---|---|---|
| one signal instead of two | a survey schema with a `birth_date` field **with no data**, and a file with three support phone numbers were stopped | the probes were only run on real lists of people |
| a file name in escaped form | `люди.json` slipped past the rails entirely: git returns a non-ASCII name as `"\320\273…"`, and no such file exists on disk as far as the check is concerned | all the probes used Latin-script names |
| `grep -c` counts lines, not matches | three birth dates in a **single-line** JSON counted as one | the sample in the probe was multi-line |

From this, two requirements for any rails: count **occurrences**, not lines, and have a probe on a
**real commit**, not just on file paths. Rails that cry wolf get disabled by the team entirely — a
false alarm is more expensive than a miss.

**Rails acceptance, 25 Sep 2026:** self-check 7 probes out of 7 (three classes are caught, three
clean files pass silently); a live run against a real file with a leaked key — the commit was
stopped, the key never made it into the message. A separate finding on ourselves: **bash 3.2 on
macOS does not support Cyrillic identifiers** — the first edition "worked" and silently skipped two
of seven probes. In shell scripts, names in Latin script, messages in Russian.

**The class is broader than Cyrillic: a substitution in a shell string can silently mean something
else.** Measurement, 25 Sep 2026, zsh 5.9 — with `BR=refs/heads/main`, the string
`$BR:tools/file.py` prints `mainools/file.py`. The colon is read as the history modifier `:t`
("take the file name"): the substitution produced `main`, the letter `t` was eaten by the modifier,
and the remainder got stuck on. No error, no warning.

What follows from this by measurement, not by guesswork:

* **Curly braces save you:** `${BR}:tools/file.py` prints the correct thing.
* **Quotes do NOT save you.** `"${P:t}"` with `P=some/dir/file.py` prints `file.py` — quotes
  protect against word splitting and glob expansion, but not against modifiers. The advice "wrap
  substitutions in quotes" does not prevent this defect.
* **bash 3.2 has no modifiers at all:** the same string prints the full path. So the same command
  means something DIFFERENT in the two shells, and a check run in bash won't reveal the defect. The
  team's machines use zsh interactively, while scripts often run under bash; the divergence shows up
  right at that seam.

Conclusion for the rule: wrap substitutions in a shell string in curly braces, verify the result by
printing it, and keep parsing and logic in Python — there are no substitutions there.


**Confirmed by a second chat on zsh, and there it's more dangerous.** A Cyrillic name breaks in TWO
ways. The obvious one: `for г in ...` — a parse error, the script crashes, visible immediately. The
silent one: the assignment `О="path"` doesn't create the variable at all, and later `cp $О ...`
gets an empty value and the command becomes a no-op — while the script itself exits with success.
So checking a shell script by "it didn't crash" isn't enough: **you have to confirm the variables
actually expanded**, not merely that there was no error. Run it on the oldest shell the team
actually has, not just your own.
