# H15. Forward proxy: a page can call the core and someone else's APIs (rolled out 13 Aug 2026)

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H15. Forward proxy: a page can call the core and someone else's APIs (rolled out 13 Aug 2026)

Cross-checked against the live OS schema: `/api/ext/core/{path}` and `/api/ext/fetch` are **live**,
the publish-time field `allowed_origins` **exists**. This removes two of our blockers at once.

The mechanics are the same in both cases: the sandbox doesn't reach another domain directly
(opaque origin, blocked by CORS), and the raw token is never handed to the JS. So the request is
made by the **OS proxy** on the server, which returns the response with CORS that the sandbox
accepts.

| Path | Where it leads | What unlocks it |
|---|---|---|
| `/api/ext/core/{path}` | `api.extella.ai` — **any** core method; the OS substitutes the real token server-side | the **`api.full`** permission |
| `/api/ext/fetch?url=…` | **your own** developer API; your own authorization is passed through, no Extella token is added | an origin in the version's `allowed_origins` — **as of 14 Aug 2026, not working, see below** |

Authentication is the same `{{app_token}}` (via the `X-App-Token` header; for core, `X-Auth-Token`
is also accepted, so the app only needs to swap the base URL). Limit **120 calls / 60 s**, body
≤ 10 MB. Redirects are not followed — there's no leaving the list of allowed origins.

**What this changes for us:**

1. **Managing a fleet of agents from a page has become possible.** Previously the conclusion was:
   `app_token` is pinned to your own agent, so Console either asks for a fully privileged
   `{{token}}` or stays device-side. There's now a third path — the `api.full` permission, and the
   token **never enters the JS**: the proxy substitutes it. The buyer sees the permission before
   installing and can revoke it.
2. **A page-type product can reach someone else's API** — Tourvisor, Bitrix24, a CRM — with no
   local server and no open CORS needed on the provider's side.

**Three honest caveats, or the rule will be read wider than it actually is:**

* **`api.full` is the entire account.** Asking for it in a product that only needs its own agent is
  the same defect as `delete_*` in tools. It's for management apps only.
* **`ext/fetch` doesn't solve the secrets question.** It passes through **your** authorization: the
  key has to come from somewhere. There's no place for it in the page's code — so either the user
  enters the key and the product stores it, or a device-side path remains. The proxy removes CORS
  and protects against reaching an arbitrary address, but it doesn't replace a key store.
* **Separate from the proxy**, a `X-Auth-Token: {{token}}` checkbox appeared in the header set. It
  sends the **full token** outward, unlike the proxy. For us — trusted server-side integrations
  only, and off by default.
