# H14. Updating without a redeploy: three ways, and they cost differently

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H14. Updating without a redeploy: three ways, and they cost differently

Verified live on 13 Aug 2026 on a published guide. The full breakdown and a working example —
`store_app/` in this same repository.

| What changes | How | What it takes from the person | When it's visible |
|---|---|---|---|
| **text, data, settings** | a commit to the content file; the page reads it from the repository | nothing | within 5 minutes |
| **the shell: layout, scripts** | replacing the page on the same version (H10) | attach the file | immediately |
| **code on the buyer's machine** | download a fresh product archive | confirm the update | immediately |

**The first way — the actual "fixed it on my end, updated for everyone."**
`raw.githubusercontent.com` returns `access-control-allow-origin: *`, so the page in the sandbox
reads the file from a **public** repository with no tokens, no app permissions, and no agent.
Measurement: a commit to content only → the window showed the new section and marked "updated as
of …," while the page itself was neither rebuilt nor re-uploaded to the store.

Four conditions, without which this method is a defect rather than a convenience:

1. **A content snapshot is embedded in the page.** The first frame renders instantly, with no
   network. A page that waits on an external source shows a blank screen if it's unreachable — a
   violation of the stop-rule "a refusal is shown in words."
2. **What arrives over the network is data, not code.** Before inserting it, strip `<script>`,
   `on*` handlers, and `javascript:`. Otherwise a content update turns into a delivery channel for
   someone else's code.
3. **The repository is public.** A private one requires a token, and there's no place for a token
   in the page's code (H11).
4. **The cache is five minutes, and it can't be forced through.** Neither `Cache-Control: no-cache`
   nor a query parameter helps — `source-age` in the response shows the age. That's fine for a
   guide; it doesn't work for data that needs freshness measured in seconds.

**A fifth condition, found on our own product on 13 Aug 2026: an update must refuse to go
backward.** The first version of the guide treated "version not equal" as "version newer" — and a
stale source **silently rolled the page back** from a fresher built-in snapshot to older text. It's
the same class of bug as "the pack was a rollback machine": every "update yourself" was returning
the previous state.

Fixed by comparing versions component by component instead of on "not equal": apply only strictly
newer ones, don't apply an unparseable version at all. And this needs a dedicated test — in an
ordinary run the defect doesn't show, because the source is usually the newer one anyway.

**The third way — code on the device, and here the rules are stricter.** Technically this is
`install.py` pulling a fresh version. But a code update arrives **inside someone else's
perimeter**, so:

* **by release tag, not a floating branch.** "Updating from `main`" means "will run whatever anyone
  pushed";
* **verify a checksum** before running;
* **state in words what changed**, and let auto-update be turned off;
* **prefer the store**: `GET /api/app-archive?app=NAME` returns the product archive with resumable
  download and an `ETag`. It's your own code, but under the platform's versioning — and it knows
  who has what installed. Updating from GitHub, nobody knows this, and support turns into "which
  commit are you on?"

A ready-made module with both sources, checksum verification, and rollback —
`templates/self_update.py`.
