# H63. Without `data-testid` hooks an app is unverifiable by a machine

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H63. Without `data-testid` hooks an app is unverifiable by a machine

Every element a person uses — a field, a button, a tab, a toggle — carries a
`data-testid`. The hook is mandatory not for looks: acceptance testing on someone else's
machine can fill fields and press buttons, but it only takes hold of **marked**
elements. Buttons without hooks do not exist for verification.

Why not "press everything": acceptance runs on a live product, and guessing at buttons
on someone else's data is not acceptable. For the same reason, buttons carrying the
words delete, post, send, or pay are never pressed, even with a hook.

Measured on 23 Aug 2026: in the 1C Agent panel the acceptance robot found six working
buttons and not a single hook — meaning there was nothing to check whether "the buttons
work for the buyer." On a scaffold with hooks, the same robot filled a field, pressed an
action, and got a real result.

Checked by an acceptance run: the "click-through" section either names the number of
buttons pressed and how many responded, or honestly says "nothing to take hold of."

**A hook's name must be unique and stable.** Permanent places (menus, tabs, the main
actions) are marked explicitly. Deriving a name from the label is a safety net for
forgotten buttons, not the primary method: the label carries counters and changes along
with the data.

Three rules drawn from real breakages on 24 Aug 2026:

- **One name on several buttons is a silent lie.** The check presses whichever comes
  first and reports "pressed," while the neighbors are never checked. Caught in the 1C
  Agent panel: three "go to registry" buttons carried a shared semantic attribute and
  collapsed into a single hook.
- **Numbers in a name don't survive.** A hook built from a label with a catalog counter
  will change along with the catalog, and the check will start looking for something
  that no longer exists.
- **Whether a name is taken is judged against the live document, not an accumulated
  list.** Screens get redrawn dozens of times; an eternal list keeps pushing the
  sequence suffix up, and the same button ends up "-13" one time and "-44" another. A
  removed button must free up its name.

The acceptance run checks this itself: the "click-through" section names repeated hooks
and names with numbers as separate lines.
