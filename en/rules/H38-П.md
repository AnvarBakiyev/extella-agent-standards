# H38-P. Appendix: what to re-read after writing to the platform

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H38-P. Appendix: what to re-read after writing to the platform

**Sent by the connectors chat on 21 Aug 2026 as a ready-made set.** H38 says WHAT to do —
re-read the artifact instead of trusting the report. This appendix says EXACTLY WHAT to
check after a write to the platform, so that the call to "check the meaning" stops being
just a slogan.

**Order of steps.**

```
read before the write → the write → transport confirmation → independent re-read
→ semantic invariants → artifact fingerprints → live-path check → next step
```

If even one point fails to check out, the operation is considered incomplete, even if the
platform answered with success.

**Transport and the target**

1. Transport success is not counted as the result. A 2xx code, a stream-completion event
   and a success field only mean the request was accepted. An independent re-read is
   mandatory after them.
2. Exactly the target object was re-read: the identifier exists, belongs to the current
   owner, and matches what was meant to be changed. The identifier is not printed into
   diagnostic output.
3. No duplicates: after creating something by its canonical name, exactly one listing is
   found. A repeated rollout reuses it, rather than creating a second one.

**The edit layer and public visibility**

4. The layer matches the intent. The card level is name, description, tags, icon, public
   visibility. The version level is number, price, permissions, page, archive, source
   snapshot, installer. Editing the card does not change versions, editing a version does
   not count as updating the card.
5. Public visibility is normalized to its meaning: true, one, and equivalent forms mean
   published. A direct comparison against a boolean true is forbidden.
6. Public visibility did not change as a side effect: after editing the card or a
   version, the state equals what it was before the operation, unless a separate publish
   command was issued.
7. H20 is checked BEFORE adding a version: for a public listing, a new version becomes
   public immediately, so the step is blocked pending the owner's separate permission.

**Version contents**

8. Exactly one version exists: one record with the expected number, belonging to the
   right listing, with a new version identifier.
9. The source snapshot is attached: the re-read version names the chosen source, the
   correct type, and attachment enabled. An empty source for a product with an expert is
   forbidden.
10. Experts are checked by their set, not by a count. All required names are present;
    wherever the interface allows it, each one's code is re-read and compared against the
    source. A single counter is not enough. Probe of 19 Aug 2026: the counter showed four
    against three unique names — the fourth entry was the installer's representation. A
    check for "exactly three" turned red on a working product, so the store's record
    count and the count of unique names are checked separately.
11. The installer is both named AND actually ran: the installer field equals the expected
    name, and then the consequence on the device is checked. A single launch flag is not
    enough.
12. Permissions match exactly: what was requested equals what was declared. Not "no
    less" — an extra permission is also a failure. After granting, the granted set is
    checked separately.

**Artifacts by fingerprint**

13. The page is read through the store: the address answers with code 200, the token
    substitution is performed, there is no account token in the response, and the launch
    marker and expected version are present.
14. The archive actually downloads. The presence of an extension in the description is
    not enough: the archive is fetched by the same path the installer will use, and its
    fingerprint matches the local candidate.
15. The installed files match the archive: the full canonical list, each file's
    fingerprint, and no leftover state or secret files.
16. File permissions are respected: executables have the expected mode, ownership is
    correct, and local secret files are owner-only.

**State and the purchase**

17. Reinstalling did not touch the state: connections, grants, the log, provider settings
    and the owner binding are compared before and after. The executable part is replaced;
    user state does not go into the archive and is not overwritten.
18. The purchase is pinned to the right version, not merely existing.
19. The shortcut leads to a stable listing address: after a new version, it stays linked
    to the listing, opens the currently purchased version, and does not contain a
    temporary address tied to a version.

**The live path and the refusal**

20. The real working path is checked: after installation, a page call, a state snapshot,
    and one safe read-only request are executed — through the store page, running as the
    app, its own expert, and the device runtime.
21. The response is parsed by its domain shape: the wrapper is stripped only on a provable
    transport marker. The presence of a `result` field is not such a marker (see H40).
22. Fields that must not change actually didn't: after a targeted edit, the publication
    state, the version list, the price, the permissions, the source snapshot, and purchase
    bindings are compared against the snapshot taken before the write.
23. The refusal is visible to the person: if an invariant fails to check out, the next
    irreversible step is not performed, the interface gets a named refusal, and the
    waiting indicator is cleared in every outcome.
24. The rollback is verifiable, not just described in words: a snapshot or the prior
    artifact is saved before the write, and after the rollback the same set of re-reads
    is run.

**The chain of facts for a hybrid delivery.** Sent by the same chat on 21 Aug 2026: after
any external action, it is not the service's response that gets checked, but the whole
chain —

```
exact listing identifier → version → purchase → product agent
→ pinned device → archive in place → the expert's first call
→ a visible result in the interface
```

In a probe, this chain caught three different failures at once: duplicate listings, a
completed purchase with no installation, and work running in someone else's scope. Its
value is that none of the three is visible at its own step — each is only found by the
next link.

---

**The danger cuts both ways — probed by the console chat, 19 Aug 2026.** An object update
actually went through, but returned an unexpected wrapper. The client treated the response
as unsuccessful and did not run the rollback, because it flagged the start of the write too
late. The result was a silent partial success: the object was changed, while the system
believes it wasn't.

Hence two corrections to the order. The "write started" flag is set BEFORE the request,
not after the response: otherwise there's no way to know whether an attempt was even
made. And before the change, a receipt listing the affected objects is saved; the
rollback touches only those objects and is likewise confirmed by a re-read. On
uncertainty, a retry starts with reading the state, not with repeating the write.
