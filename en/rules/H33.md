# H33. The desktop's origin holds the token: someone else's code sits right next to it

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H33. The desktop's origin holds the token: someone else's code sits right next to it

**Measured against the OS's live frontend on 21 Aug 2026** — file
`desktop.bf512c0e78dc.js`, 165 KB. Not a retelling of documentation: every statement
below was verified by reading the code. To re-verify: `curl https://os.extella.ai/desktop`,
take the name `desktop.<hash>.js` from the response, download it from `/os-static/`, and
read it.

**The root cause is named right in the OS's own code.** Seller pages open in a frame
sandboxed WITHOUT `allow-same-origin`, and a comment explains why: the proxied page lives
on the OS's origin, and without the sandbox it would be able to reach `window.top`,
`localStorage`, and the user's token (H24 and H32 talk about the same thing).

The app inside the window is evicted from the token. **Three other surfaces are not.**
They execute code right within the desktop's own origin, where the token lives.

**1. Custom actions — right-click menu items.** The script runs as
`new Function('app','os', code)` right in the desktop's context. Browser globals are
available, meaning `localStorage` and the token are available. Next to it there's a
"Load from file…" import: someone else's script arrives as a file.

**2. Store extensions — a seller's code in the buyer's browser.** When an app is
installed, the `/api/purchase` response may bring a `store_extensions` field: the
seller's JS, which executes on the user's pages. Such entries are marked `fromStore` and
`locked` — a lock icon and the word Store show on screen, editing is disabled. Updates
are pulled by polling `/api/my-extensions` every 12 seconds while the embedded browser
window is open.

**3. Custom headers with substitution.** The OS proxy replaces `{{token}}` with the full
account token, `{{email}}` with the mail address. The app gains the right to reach the
whole Extella REST on the person's behalf. There's exactly one barrier: a consent dialog
before the first run.

**Two caveats on point three, both from the code.** Consent is asked once and remembered
(`tokenGrants` in the state), it's not raised again. And it only checks for the presence
of `{{token}}` or `{{email}}`: a third substitution, `{{agent_id}}`, doesn't raise the
dialog at all.

**The rule.** Someone else's action script, someone else's extension from the store,
someone else's header with `{{token}}` are not installed without reading the code. Your
own — fine, someone else's — never. This is executing someone else's code inside your own
cabinet, right next to the token — that is, more dangerous than any app from the store:
the app is held back by the sandbox, these three surfaces are not.

A map of the desktop's other capabilities is `OS_CAPABILITIES.md`; the same three
surfaces are described there from the benefit side, with a reference back to here.
