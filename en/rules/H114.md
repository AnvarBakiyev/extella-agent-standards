# H114. A GATE IS ACCEPTED ONLY AFTER A RUN AGAINST A LIVE SUBJECT

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H114. A GATE IS ACCEPTED ONLY AFTER A RUN AGAINST A LIVE SUBJECT

**Measurement, 25 Sep 2026, across the whole set.** The `run` command in `run_all_gates.sh` only
launches `--selftest` — it asks the gate "are you working" on hand-built probes. A live run is a
separate line, and five repository gates didn't have one. What this was hiding:

* `check_surface_classes` **is red on live data**: of 14 desktop cards, 11 have no declared class,
  plus the passport fails on three requirements. In the set, the gate had been green the whole
  time.
* `check_toolkit` **printed not a single line in 120 seconds**. The cause turned out not to be in
  the gate: the response-shape check called a live local model (a 180-second timeout), and on a
  machine **without** a model it silently checked nothing — emptiness passed as success. Now the
  contract is checked by reading the code: 0.8 seconds, and it always works.
* `check_agent_drift` returned 0 with the words "SKIPPED: no passports found": there's no subject
  in the clone, and emptiness is reported as success.

**And five independent cases where the FIRST edition of a gate written over the text lies on the
live tree almost every time:** `check_device_pinning` — 7 false alarms,
`check_file_size_claims` — 2, `check_counted_claims` — 4 of 7 hits, `check_surface_classes` in the
first edition of the fix — 11 products at once (any divergence between copies was declared a
failure, even though a working branch legitimately differs from the canon), and the path check
described in item 6 — 18 hits, all of them false. None of these errors show up on hand-built
probes: the author writes probes for what they've already thought of.

**Rule.**

1. **A live run is proof of acceptance, and it happens where the subject lives.** A run that
   printed "skipped" does not count as proof.

   **"Where the subject lives" also means which clone is the live one.** Measurement, 25 Sep 2026:
   one product had seven clones on the machine, exactly one of them live. The gate took the first
   one alphabetically — a corpse from a dead branch; the fallback rule "look in
   `~/Documents/Extella`" picked a different corpse, a clone from 12 August while the live one was
   from 25 September. Both times the gate ruled confidently and wrongly. The live clone is
   determined by the **freshest HEAD**, not by name order and not by directory convention; a
   `passport:` declaration line takes priority over both.

   **A run that found no subject is not acceptance, even if run against someone else's tree.** The
   first run of `check_gate_acceptance` over the canon keeper's tree gave 0 out of 32 and zero
   false alarms — not because the gate is good, but because there wasn't a single acceptance line
   there. The second run, once a subject appeared, became the acceptance. Distinguish: "checked
   against someone else's tree" from "checked against someone else's tree where the subject
   exists."
2. **Every false alarm from a live run becomes a permanent probe.** If there were few hits and all
   of them were false — the check is removed entirely, not tuned: a false alarm is more expensive
   than a miss, because a lying gate gets disabled along with its benefit.
3. **An acceptance line in the header, with a date.** The word ACCEPTANCE at the start of the line,
   a date, a colon, and what the run produced. The date is mandatory: a count of false alarms is a
   claim about a past measurement (H113). Backticks are excluded — otherwise a format example in the
   documentation counts as a fulfilled requirement; this very check caught itself doing this and
   scored itself 11.1% instead of 8.3%.
4. **A gate that doesn't fit within a reasonable time doesn't live in the set.** 600 seconds for a
   subprocess means it will never be run even once.
5. **Per-product gates are not an exception to this.** They need an argument — a product folder, a
   policy file, a repository address — they're called by `stage_gates` with a target, and there's
   no live run for them in the general set, by design rather than oversight. Thirteen of twenty in
   the set are like this: before demanding it, distinguish the subject.
6. **A link, path, or locator is considered checked only once it's been OPENED**, not once it's
   syntactically correct. Two cases from 25 Sep 2026, independent: the passport gate checks the
   form of `binding_ref` and cannot check that the file actually exists at that path — the author
   caught himself having entered a nonexistent path, and did the right thing by CREATING the file
   rather than fixing the text. The second: the path existed but led to someone else's copy — one
   agent's passports exist in six different clones on the machine, the gate took the first
   alphabetically (a copy from a dead branch) and passed judgment on it, while the author was
   writing to a different one. The form was correct, the subject wasn't. This is the same reason
   behind item 1's requirement, "where the subject lives": a live run against the wrong copy is not
   proof.

   **There is no repository-wide check for this, and here's why.** I tried: search the text for
   paths inside the repository and open each one. Of 167 paths, 18 didn't open — and all of them
   turned out to be false alarms. Texts legitimately reference neighboring repositories with
   ordinary relative paths (`docs/INCIDENT_KV_SCOPE_SHADOWING.md` is explicitly named as belonging to
   the "core-portal repository"), and the `templates/app-recipe/README.md` template describes the
   paths of a FUTURE product, not ours. There's no machine way to tell these apart. Per item 2, the
   check was removed, not tuned. Making it possible would need a convention: a reference to another
   repository names that repository. Introducing that now is a separate piece of work.

   The place this rule actually checks is narrower and different: wherever a gate checks a SPECIFIC
   locator field (`binding_ref`, a path to a passport, the address of a canonical copy), it must
   open it, not just verify its form. That's a per-product gate, not a repository-wide one.

Held in place by `tools/check_gate_acceptance.py` as a ratchet: the share of accepted gates can
only grow. There's deliberately no flag day — requiring an acceptance line from all of them at
once would mean fifty edits nobody would read, turning acceptance into a ritual.
