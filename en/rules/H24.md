# H24. SOMEONE ELSE'S APP IN AN OS WINDOW: five refusals, and each one is silent

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H24. SOMEONE ELSE'S APP IN AN OS WINDOW: five refusals, and each one is silent

**Probes on 15–16 Aug 2026.** We put three ready-made web apps into an OS window
(excalidraw, drawio, pdf.js) and spent a day figuring out why "everything is green" and
nothing works. Five causes, and not one of them produces an error in the logs.

**0. WHY it's like this — read from the OS's own code on 16 Aug 2026, and this is NOT a
browser defect.** The shell opens the seller's page in a frame with `sandbox` WITHOUT
`allow-same-origin`. The OS's own comment explains the decision: the proxied page lives
on the OS's origin, and without the sandbox it would be able to reach `window.top`,
`localStorage`, and the user's token. The sandbox gives the frame an "opaque" origin:
scripts, forms and windows work, but access to someone else's data does not.

All five refusals below follow from this. And it also follows that asking for "please
allow storage" is pointless: that's a request to remove the isolation between the seller
and the user. The right request is to **give the sandbox ITS OWN storage from the OS**
(for example, message passing with the shell, or a KV scoped to the listing), while
keeping the isolation intact.

**THREE DOORS, AND THEY BEHAVE DIFFERENTLY** (clarified by the Schema Board chat,
16 Aug 2026):

| door | behavior | what to shim it with |
|---|---|---|
| `localStorage` / `sessionStorage` | stays silent, work is lost silently | substitution → a file on disk |
| `document.cookie` | throws `SecurityError` | an in-memory jar |
| `IndexedDB` | throws `SecurityError` | a polite refusal via an event |

**The silent door is dangerous for data, the throwing ones bring the whole app down.**
Excalidraw crashed on the very first line that read a cookie: a white screen, and the
reason is in a console that doesn't exist inside the OS window. Hence the rule: all three
must be shimmed, but only where the native behavior throws; you must not break something
that works for the sake of a safety net.

**1. The OS window is someone else's page, and storage there is closed.** The product
opens inside an iframe within `os.extella.ai`; the app becomes a "third party," and the
browser closes off `localStorage` to it (`SecurityError`). App behavior differs, and the
second case is more dangerous than the first:

* **drawio** shows its own English "Error loading page. Please try refreshing";
* **excalidraw** OPENS FINE and silently loses drawings when the window is closed.

Hence the acceptance criterion: not "the page opened," but **"the work survived a window
reload."** Everything else is self-deception.

**2. The app's service worker takes over the whole port.** excalidraw and drawio
register a SW with scope `/`, and any address on that port serves their copy — our file
placed next to the app never gets through at all. As long as the SW is alive, edits to
`index.html` never reach the browser. The fix: remove the SW file (`service-worker.js`,
`sw.js`) — on a 404 the browser unregisters it itself.

**3. A script with Cyrillic before `<meta charset>` silently fails to run.** The browser
reads the Russian text as Latin-1, gets syntactic garbage, and quietly skips the block.
Insert your own code only AFTER the encoding declaration, and if there isn't one, declare
it yourself, inside a marked block (otherwise removal will leave the declaration behind
in someone else's file).

**4. The browser serves a stale `index.html` from cache.** The edit is in the file, it's
in the `curl` response, and it's not in the window. The app's server must serve pages
with `Cache-Control: no-store` and declare `charset=utf-8` — `http.server` does neither.

**5. Not every app is fit for a window.** drawio refuses to work inside someone else's
frame EVEN when given storage — that's its own decision, not our breakage. Such an app
gets removed from the lineup; you cannot sell as a product something that only opens in
its own separate window. **"Open in a separate window" is a workaround, not a solution**
(the owner's words, 16 Aug 2026).

**What comes out of this as workable.** The app's storage is moved to disk: its own
server serves a storage endpoint, and an injection into the page replaces `localStorage`
with a write to a file. The work stops depending on the browser, it becomes visible as a
file, and an agent can read it. Ready-made pieces: `tools/cabinet_server.py`,
`templates/storage_shim.html`, `tools/inject_probe.py` (the edit is marked, removes
cleanly, with a `.до_пробы` copy kept alongside).

**Editing someone else's code — only like this:** marked, idempotent, removable down to
the byte, with a copy kept alongside. Verified by the tool's self-check, not by eye.

**Four more refusals, each costing an hour** (Schema Board chat, 16 Aug 2026):

* an app may intentionally not save in a background tab. Check only in the visible
  window, otherwise you'll call someone else's optimization a defect;
* **your own page interceptor (service worker) takes over the whole port** and serves an
  old copy. Renaming files isn't enough: the registration lives in the browser
  separately. The most reliable fix is a **new port**;
* **your own stub must mark its own refusal** (`__extella_expected`), otherwise the
  window will declare a working app crashed — on its own polite refusal;
* **metadata sent with a version lands on the version.** The CARD's name, description
  and tags live on the listing and are updated separately — `POST
  /api/edit-listing/{id}` (confirmed by reading the storefront). This is an amendment to
  H23: a tag is required with the version, but it does not change the card.

**The method that worked after five blind loops: make the window name the cause itself**
— "the browser didn't let it in" / "the app is silent" / "the app crashed: name,
message, file:line, stack." **Build the diagnostics as the first step, not the seventh.**
This is more valuable than every other rule on this page: without it you fix things at
random, and every loop is only cheap in words.
