# H34. The launch device and the listing form: three places where the request body decides the wrong thing

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H34. The launch device and the listing form: three places where the request body decides the wrong thing

**Findings from a chat building on Extella, 20–21 Aug 2026. The points about the device
were independently re-verified here; the ones about the icon and the listing form were
accepted with a correction, given below.**

**1. REST does not accept the `target` field at all.** A lone `target` returns 422:

```
{"type":"extra_forbidden","loc":["body","target"],"msg":"Extra inputs are not permitted"}
```

Re-verified on 21 Aug 2026 against `POST /api/expert/run`. **Sending both fields at once
brings the request down exactly the same way** — the same message, about `target`. So the
old habit of sending `target` and `targets` together for compatibility's sake is now not
a safety net but a guaranteed refusal.

**What this cancels out.** Previously a lone `target` was accepted silently and the work
went to the default device — a quiet handoff to someone else's machine. Now the field is
rejected explicitly. For REST there's one rule: only `targets: [device_id]`, as an array.
For the JS bridge (`etb_run_expert`), `target` is still needed — these are different
contracts, and they must not be confused.

**2. A sleeping listener answers 500, not a meaningful refusal.** `targets: [device]`
against a device that's asleep gives `500 Target … is unavailable`. It reads as "the
device is dead," though it's fixed by waking the listener. Tell them apart in advance:
`search_targets` shows `available: false` before it wakes up — check there, not by the
response code.

**3. A page-type product must not be published attached to an agent.** Publishing with
`source_type=agent` and `attach_agent=1` sets the product up as an add-on to the agent,
with no window: the desktop shows an icon, but the web app doesn't open. On top of that,
the platform spins up a clone agent **for every installation** — each entry in the
purchase list gets its own identifier. A page-type product is published without
`source_type`, `attach_agent`, or `source_id`.

**4. The icon is not saved on the first publish.** The `icon` file in the multipart
upload is accepted, there's no error, and the listing ends up without an icon. Deliver it
as a second step: `edit-listing/{lid}` with the `icon` file. This is the same class of
issue already described for adding a version: only `edit-listing` changes the icon.

**7. A boolean field arrives as a number.** The listing list returns the publication flag
as `1`, not as a boolean truth value. A check that compares it directly against a boolean
treats a published listing as absent — and the next run either creates a duplicate or
carries on a closed operation on a public product. Cast to boolean before comparing, look
for the listing independently of its publication state, and refuse rather than proceed
when it's unclear (probed by the connectors chat, 19 Aug 2026).

**6. The expert's code sits in `expert_code`, and its length is counted in characters.**
A homegrown re-read that reads `code` always gets an empty string and "passes" by
default — the check goes blind without turning red. This was independently found twice:
once on 29 Jul 2026 by one chat and again on 21 Aug 2026 by another, almost a month
apart. The first finding stayed in a personal log and never made it into the shared
canon, so the second chat spent time on it all over again. Compare by content, not by
length: length arrives in characters, while Cyrillic takes two bytes, so size comparisons
diverge exactly where the text matches.

**A correction to the original finding.** It said the icon field is absent from the
listing list entirely. The probe of 21 Aug 2026 says the opposite: both `GET
/api/listing/{lid}` and `/api/my-listings` carry `has_icon` and `icon_ext`. There is
something to check the result against, and it must be checked — by `has_icon`, not by
how the card looks.

**5. A split package breaks links between its own pages.** After breaking one product up
into several listings, internal links keep pointing at files that moved into a
neighboring app; the button opens a white screen with `{"detail":"No such asset"}`. It's
fixed in two passes: first publish, to learn each listing's identifier, then rewrite the
foreign links to absolute `/app-page/{lid}/…` and cut a new version. Links show up both
in single quotes and in nested folders — build the map from the actual file layout, not
from the root.
