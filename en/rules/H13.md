# H13. CANCELED 13 Aug 2026 — token-based isolation no longer exists

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H13. CANCELED 13 Aug 2026 — token-based isolation no longer exists

**The section below describes behavior that no longer exists.** Left in full because decisions were
built on it (publishing the guide manually by the owner, reading the token from a separate file) —
and because it's a textbook example of a fact that went stale within a day.

**Measurement, 13 Aug 2026, the same device token:** `my-listings` returns **19 listings**,
`my-purchases` — **21 purchases**, including everything the owner had seen on screen ("Test 1,"
"Recruiter Panel Shell," "Lawyer," "Telecom Demo"). A day earlier the same token saw **4**. What
exactly changed on the platform side, I don't know; the platform's author was working on token
management with access levels around this time.

**Current rule:** an account token sees the account's storefront. The workaround "only the owner
publishes manually" is no longer needed, nor is a separate file holding the storefront's token.

**What remains useful from H13:** a quick diagnostic. If the API's list disagrees with what a
person sees on screen — don't argue and don't declare a defect, **cross-check the specific
`listing_id`**. Our account has two different listings with similar names living side by side
("Predictive Sales" and "Predictive Sales (OSINT)"), and one of them **has no page at all**: a
request to it answers "This app has no web page." Confusing the two is a ready-made false
diagnosis.

### H13 (historical text). The storefront belongs to a TOKEN, not to the account (12 Aug 2026)

**The most expensive finding of the day, by time spent.** I published an app, the owner opened his
own store on the same account — and did not see it at all.

The reason is written in the platform's documentation but wasn't read as a consequence: the
owner's internal key is `sha256(token)`, and "all user data (desktop, purchases, listings,
balance) is isolated by the owner of the **token**."

**So one account has as many parallel stores as it has tokens.** Our live account has
**eleven** of them (`list_tokens`): service ones, auto-created ones, colleague invites, a toolbar
session. Publishing with a service token went into its own container: the API honestly showed the
listing, the interface honestly did not show it — and both were right.

The tells that show this rather than merely suggesting it:

* one name differs between the interface and the API (for us — "Predictive Sales (OSINT)" versus
  "Predictive Sales"): these are **different listings in different containers**, not a rename;
* the listing count doesn't match by a wide margin (14 versus 4);
* a freshly published item isn't in the interface, yet `my-listings` returns it.

**Rule:** publish with **the same token** the owner uses in the interface. The token from
`~/.extella/api_token.txt` is **not fit by default** for publishing into his storefront — first make
sure it's the right one. A quick check before publishing: compare `my-listings` with what the owner
sees on screen. If it doesn't match — don't publish, ask.

**What must never be done:** cycling through the account's tokens to find the right one. This looks
and behaves like credential stuffing, and the environment stops it — rightly so. Colleagues' tokens
(`invite: …`) are not to be touched at all: someone else's data sits behind them.

**A simple workaround with no tokens at all:** the owner publishes a page-type product himself
through the OS form — the interface file in the Web page field. Then the listing lands, by
construction, in the very container the owner works in.

**Platform response received on 12 Aug 2026 (from the platform's author): this is intended for
now.** A separate token-management page with access levels is being prepared, and then isolation
will stop being a problem. So this is **not a defect but the current model** — the question is
closed and shouldn't be raised again.

Until that page appears, the rule above stands: publish with the token the owner uses in the
interface, and treat a mismatch between `my-listings` and the screen as a stop signal. Once token
management appears, revisit this section: isolation will most likely become configurable, and the
ban "don't publish with someone else's token" will turn into "pick the right access level."
