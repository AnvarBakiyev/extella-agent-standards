# H48. A DIRECT URL TILE IS FRAGILE: HTTP/1.1 and app-page instead of it

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H48. A DIRECT URL TILE IS FRAGILE: HTTP/1.1 and app-page instead of it

**Probe from the "Documents" chat, 21 Aug 2026.** Two errors from one root: a shortcut
that leads to a direct local address, rather than to the listing card, looks broken
while the app is actually working.

1. **The OS window requires HTTP/1.1 with keep-alive.** A local server on HTTP/1.0
   without keep-alive sometimes gives the OS window "The site didn't render" while the
   server is alive — the requests are in the log, there is no render. After moving the
   server to HTTP/1.1 it stopped reproducing. Rule: the product's local server speaks
   HTTP/1.1. This is the same class already recorded for `X-Frame-Options` and
   `Cross-Origin-*` — the window downloads the document and silently refuses to draw it.

2. **The favicon of a direct shortcut is cached forever.** The desktop takes the icon of
   a direct url once and holds it in the Electron cache: the server is already serving
   `favicon.png`, but the tile stays a globe even after the state refreshes. It looks
   like "the cache didn't update," even though the server does serve the icon.

**The fix for both is canonical and single:** not a direct url tile, but the listing
card and the page at `/app-page/{lid}/` — the storefront supplies the icon, and the
window is drawn through the verified proxy. A direct local address on the desktop is for
debugging only, not for the product. This confirms what has already been said about
shortcuts: a direct address is fragile, the canon runs through app-page.
