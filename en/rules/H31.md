# H31. AGENT PERMISSIONS: the platform accepts names that don't exist in the runtime

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H31. AGENT PERMISSIONS: the platform accepts names that don't exist in the runtime

**A designer's finding, 18 Aug 2026, confirmed by an independent probe the same day.**

The platform has two generations of tool names. The new generation starts with a verb
(`search_concepts`, `list_rules`, `get_kv`), the previous one starts with a noun
(`concept_search`, `rules_list`, `kv_get`). The live MCP server serves **only the new
generation**.

The platform accepts the old names silently: `agent/create` answers 201, `agent/get`
returns the whole list back, the checkboxes are ticked in the interface. Such a tool
never comes up in the runtime, and the agent only finds out at the moment it's called.

**Probes.**

| what was measured | declared | available in the runtime |
|---|---:|---:|
| the designer's agent, freshly created | 12 | 4 |
| "Travel agent," a live client product | 18 | 5 |
| two throwaway agents, both name generations | 6 and 6 | launch unavailable, see below |

For "Travel agent" the runtime showed `web_search`, `get_expert`, `run_expert`,
`check_task`, `get_default_target` — and not a single `kv_*`. The product declared it had
its own memory and did not have it. It has no blanket allowance, so no substitution
happened — the thirteen permissions simply weren't there.

The throwaway agents, created through `agent/create`, couldn't be launched at all: the
platform returns `pro_key_required` on any run of an agent created via the API. That's a
separate, known refusal, unrelated to the names.

**What to do.**

1. Declare permissions using only new-generation names. The mapping between old and new
   names is in `tools/check_agent_tools.py`, which also names the names with no
   equivalent.
2. After flashing permissions, **ask the runtime**, not `agent/get`: one run asking it to
   list the available tools. The permission list in the agent's card does not prove this.
3. The `check_agent_tools.py` check is now red on previous-generation names. On the
   account, as of 18 Aug 2026, 28 of 30 agents carried them. A census of the "Building on
   Extella" chat on 21 Aug 2026: of 69 agents, 51 can run experts, 32 can find and run
   them; `agent_extella_default` can't do either at all (confirmed by the gate).

**Addition, 20–21 Aug 2026, from someone else's probe.** Re-flashing permissions through
`agent/update` does NOT fix the mismatch: the declared list is accepted whole again, and
the same four remain in the runtime. The working workaround is not to fight for the
permission, but to wrap the missing piece into an expert: a knowledge search expert
reaches `/api/concept/search` on its own with the device token, and the agent calls it
through the available `run_expert`.

**And a consequence for instruction text.** The agent executes a short tool name as if it
were an expert's name: an instruction to call `rules_list` turns into
`run_expert("rules_list")` and ends in the refusal "Expert not found." In instructions,
name tools by their full runtime name (`rules_list_mcp_extella`) and state explicitly
that it is a tool, not an expert. Tools that don't exist in the runtime should not be
mentioned at all — the agent will try them.

**Why this is more dangerous than an ordinary typo.** A wrong name causes no error either
on writing or on reading. The agent's card looks correct, the passport checks out, the
permissions gate passed. The refusal shows up in the client's work and looks like a
broken product, not a missing permission.
