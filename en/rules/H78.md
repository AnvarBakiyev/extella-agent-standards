# H78. Refusal handling lives in one place, or copies drift apart silently

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H78. Refusal handling lives in one place, or copies drift apart silently

**Measured 23 Aug 2026.** A buyer saw this line on screen:

    The OS answered 502 · core /api/expert/run failed: HTTP 500: {'status':
    'error', 'message': 'Target device-… is un

— the core's raw response together with a Python dict. On another screen of the same product,
the same cause had been translated into words: "Device unavailable. Fully quit Extella
(⌘Q)…". The answer wasn't in the platform: refusal handling existed **in two copies** — the
install path and the storefront path. The translation for `Target … is unavailable` had been
added to one of them, the other stayed as it was, and nobody noticed: both "worked."

**The norm.**
1. Translating platform refusals is **one** function for the whole product. A second handler
   with the same branches is not code duplication, it's guaranteed behavioral drift.
2. Raw platform text is **never** shown to a human, including for an unfamiliar cause: it goes
   to the window log, the human gets words and a next step. Truncated English with curly braces
   isn't diagnostics, it's an admission that the product didn't understand its own refusal.
3. The "cause unknown" branch must exist and also give a step. Checked by the page contract:
   the function's singularity, both call sites, absence of raw text, and a live run against the
   platform's verbatim response.
