# H32. MICROPHONE AND CAMERA ARE UNAVAILABLE IN AN OS WINDOW. And it's the same hole as with storage

### H32. MICROPHONE AND CAMERA ARE UNAVAILABLE IN AN OS WINDOW. And it's the same hole as with storage

**A colleague's finding, 20 Aug 2026, confirmed by reading the OS's live code.** Verified
on two independent products: a tender system and HR Desk. In both, the page does the
recording, and the device-side part only decrypts the finished file.

The OS window creates a frame with this set:

```
sandbox="allow-scripts allow-forms allow-popups allow-modals allow-downloads"
```

What's missing: `allow-same-origin`, an `allow=` attribute at all,
`allow-popups-to-escape-sandbox`. Consequences: `getUserMedia` is rejected; a workaround
through a separate window doesn't work, because the popup window inherits the same
sandbox.

**What the sandbox does NOT cut off — downloading.** `allow-downloads` is in the set,
verified by reading the live code on 21 Aug 2026. A counter-finding from another chat
explained a blocked download by the absence of this permission — that explanation is
wrong, and following it would have led to fixing the wrong thing. The real cause is
different: the message `Blocked host (internal address)` is printed not by the shell but
by the proxy, which cuts off internal addresses; there is no such string anywhere in the
shell's code. The working workaround is the same one that chat found: the device places
a copy of the file straight into the person's downloads, and the download button is
hidden in page mode.

**The cause is named directly in the code**, and it's reasonable: seller pages are served
from the OS's own domain, so without the sandbox such a page would be able to reach
`window.top`, storage, and the user's token.

**Hence the key point for the conversation with the platform: this is the SAME hole as
with storage (H24).** Both grow from one thing — the page lives on someone else's origin.
So there aren't two separate requests:

| what to ask for | what it closes |
|---|---|
| **its own origin per listing** (a subdomain) | storage, cookies, IndexedDB AND device permissions, all at once |
| `allow="microphone; camera"` on the frame | only devices, and only if the origin stops being empty |

The second one alone may not work: a frame without `allow-same-origin` has an empty
origin, and there's nothing for the browser to attach the permission to. This is worth
verifying with a probe before proposing it as a ready solution.

**What the product should do until this is fixed.** Accept the ready-made recording file
and **do not advise going into system settings**: the sandbox returns the same
`NotAllowedError` as a person who clicked "Deny." The advice "allow it in settings" sends
the person to a place where everything is already allowed. How to tell the difference —
in the `extella-ui` skill, section 4b.


**Addition from the console chat, 19 Aug 2026.** The refusal repeated when reading a
receipt, meaning this is not a one-off oddity. The working parsing approach: strip ONLY
named wrappers, and parse a Python dict safely — as an allowed subset, without executing
code. After parsing, a strict check of the schema, namespace, state and fingerprint is
mandatory: having been parsed does not yet mean being correct.
