# H62. The app is an internal panel: outward only by message, there is no direct request

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H62. The app is an internal panel: outward only by message, there is no direct request

The product page consists of TWO parts, and confusing them is costly. The platform
supplies the wrapper: it holds the app token and itself makes the request to
`api/app-agent/run`. Inside the wrapper lives the sandbox frame, and **the author's app
is that frame**. The frame has no origin of its own (it is empty), so a request from
the panel outward does not go through, in principle: the browser refuses it before the
network is even reached.

Hence the one legitimate path: the panel talks to the wrapper **by message**
(`etb_run_expert` outward, `etb_expert_result` back), and the wrapper is the one that
goes to the platform.

Verified 23 Aug 2026 by a probe on the live 1C Agent: the wrapper carries both
`app-agent/run` and both halves of the message protocol at once; the inner frame is
created by the wrapper's own code. Separately proven by contradiction — a utility script
run inside the frame could not send a request outward and only reached the observer by
message, upward.

Without this rule the author writes a direct request in the panel, gets "could not get a
response," and looks for the fault in the platform, where there is none.

Amendment to the earlier record: the wording "two different ways to communicate, pick
whichever fits" is wrong. There is one way; the two parts are the platform's wrapper and
the author's panel.
