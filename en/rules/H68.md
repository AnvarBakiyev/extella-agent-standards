# H68. Adding your own language is done through a container, and four things break it silently

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H68. Adding your own language is done through a container, and four things break it silently

The mechanism was verified live on 28 Aug 2026: an expert in Rust was built and run on
a Mac through actual CSPL, output `{"привет": "мир", "сумма_1_10": 55}`.

**A language handler is registered as an ordinary expert in `fython`.** No special
rights are needed: the expert calls `disnet.Disnet(...).container(code=…,
func_name="<language>", container_path="<language>", args=None, kwargs=<envelope>,
cspl_type="fython", push=False)`. After that, any expert declares `cspl="<language>"`,
and its source gets this handler. The handler itself runs as `fython` — the language is
added without changing the platform.

Four things, each of which produces a silent or misleading refusal.

**First: `save_directory` is the container folder itself, not its parent.** By default
the value is relative (`containers_folder`), and that's correct, because the expert runs
with the listener's working folder. A parent value in this field means the container
lands next to the folder, the registration answers "recorded," and the language does
not appear.

**Second: `push=True` sends the container to the server, while the listener takes the
local file.** Locally, write `push=False`. A "sent" response with no local write means
an earlier version of the handler is running, and the edit hasn't taken effect.

**Third: the service has a stripped-down environment.** The desktop app launches the
listener with `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, so tools from `~/.cargo/bin`,
`/opt/homebrew/bin`, and similar locations are invisible. The refusal looks like "the
compiler isn't installed" on a machine where it is installed, and the advice "install
it" doesn't help — the install would land in the same place. The handler must look for
the tool itself and add its directory to the build environment.

**Fourth: the source arrives in the field `filtered_source_code`.** A handler that only
accepts `code` gets an empty string and complains about an empty file — for compiled
languages this looks like "no main function." Accept both names.

**Fifth: backslashes do not survive the path through `fython`.** A grammar check based
on regular expressions inside a hardcoded handler silently stops working: a correct
`SELECT` was rejected as "not a read query," even though the handler received it in
full (probed 28 Aug 2026). In handlers that travel as a string, checks are written as
plain string operations, without regular expressions.

The full envelope the handler receives (probed with a separate diagnostic language):
`code` arrives **empty**; the expert's source sits in `filtered_source_code`; the run
parameters are in `kwargs`; `func_name` holds the name of the EXPERT, not the language;
alongside it come `args`, `cspl`, and `run_time`.

Separately, about the device: the run is pinned with `targets=["<device_id>"]` (the id
sits in the listener's working folder). Without pinning, the job goes by default routing
to another device, where there is neither the container nor the tool, and the refusal
reads as the language being broken.
