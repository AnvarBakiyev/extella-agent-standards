# H96. WINDOWS ACCEPTANCE IS ON x86-64. THE ARM VM HAS WORKED SINCE 20 SEP (CORRECTION BELOW)

### H96. WINDOWS ACCEPTANCE IS ON x86-64. THE ARM VM HAS WORKED SINCE 20 SEP (CORRECTION BELOW)

**Measured 20–21 Aug 2026 from device logs.** A Windows test stand in Parallels on an Apple
silicon Mac is Windows-on-ARM. The `extella-listener` package has no `win_arm64` wheel (there is
`win_amd64`, `manylinux`, `macos_arm64`; no sdist is published). The app's built-in `uv` resolves
the platform as `win_arm64` → "no wheels with a matching platform tag" → the listener crashes
five times in a row → the device is stuck forever at "Target unavailable." For Windows x86-64
users — the wheel is there and everything installs.

**Cost:** the stand was down since 20 Aug, an hour spent parsing logs, a false conclusion of
"broke after the app update."

**CORRECTION 20 Sep 2026: the rule is outdated, ARM works.** A measurement today on the same
ARM VM (Parallels, Apple silicon, owner's machine): an expert sent by the platform ran and
returned `{'system': 'Windows', 'release': '11', 'arch': 'ARM64', 'python': '3.12.7', 'encoding':
'utf-8'}`. That is, the listener installs and runs on Windows-on-ARM natively — either the
`win_arm64` wheel appeared, or it's built from source. The ARM ban is lifted; x86-64 remains
preferred for acceptance only because it's the buyer's mass-market platform, not because ARM
"lies."

**Rule (21 Aug edition, before the correction; the part about a "false red" is outdated).**
"Will it install for a stranger" acceptance on Windows is done only on an x86-64 machine (VPS or
hardware). An ARM VM on a Mac gives a false red from the platform and gives no green at all. The
ARM workaround (x64 CPython + `UV_PYTHON_PREFERENCE=only-system`) is for our own work only, not
for acceptance: it checks our workaround, not the buyer's machine. The wheel fix belongs to the
tech department (`report_issue` sent 21 Aug).
