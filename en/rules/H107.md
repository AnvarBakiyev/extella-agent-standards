# H107. DEVICES AND THEIR RECORDS: WHO PICKS THE MACHINE, WHEN, AND WHAT IT DEPENDS ON

Full corpus — `DEPLOY_REQUIREMENTS.md`; rules index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H107. DEVICES AND THEIR RECORDS: WHO PICKS THE MACHINE, WHEN, AND WHAT IT DEPENDS ON

**Measurements 24 Sep 2026, a live account, the probe expert `wz_ping` (returns the machine's
name).** This section answers a question that until now was settled by guesswork: why does the
work end up on the wrong machine.

**Two different objects, and confusing them is costly.**

* **Device** — the machine itself. Its identifier is born on the listener
  (`~/.extella/device.txt`), visible in the app's status bar and in
  `Library → System → Devices`.
* **Target record** (`target`) — a named reference to a device within a scope:
  `add_target {device_id, description, global}`. One device can have several records
  (the owner's Mac has three names: "work listener," "live listener," "Predictive Sales
  buyer's device").

**Calls take DEVICE identifiers, not record identifiers.** Measurement: `targets` with
the Mac's record `target_id` (`efe19380…`) → `Target efe19380… is unavailable`, even
though the machine is on and running. The error lies: it's not "unavailable," it's "wrong
kind of identifier."

**How the platform picks the machine — by call path:**

| Who calls | What sets the machine | Measurement |
|---|---|---|
| `run_expert` / `/api/expert/run` with `targets` | a list of **candidates in order**, the first available one is taken | `[VPS, Mac]` → VPS; `[Mac, VPS]` → Mac; `[dead, VPS]` → VPS with no error; `[dead]` → `Target … is unavailable` |
| the same **without** `targets` | the account's default device | before the default was changed → VPS, after switching to the Mac → Mac |
| a product page via `app-agent/run` without `targets` | **the platform's own choice, and it differed from the default**: on 22 Sep the default was the VPS, but the call went to someone else's machine (letter §46); on 24 Sep — to the Mac | the platform doesn't document a selection rule |
| an agent, when it calls the expert itself | **there is nothing to pin it to**: `run_agent` has no `targets` parameter | the agent decides on its own; hence "works for me, doesn't work for my colleague" |

**THE DEFAULT IS PER AGENT (measurement 25 Sep 2026, closes the open question in H107).**
`/api/defaults/get_target` was queried with different `X-Agent-Id` on the same account:

| agent | its default machine |
|---|---|
| `agent_extella_default` | VPS `85800354…` |
| the 1C Agent's agent (`agent_9Oig…`) | Mac `24f37e45…` |
| the guide app's agent (`agent_HiSO…`) | Mac `24f37e45…` |

This explains the case from letter §46: the page call without `targets` did not go to the
"account's default" device, but to the default of **this app's own agent** — which at the
time was a machine on a different account. There was no randomness in the choice at all.

**And the default shifts under you.** The same day's measurement: on 24 Sep the default for
`agent_extella_default` pointed to the Mac (confirmed both by request and by a run), on
25 Sep — back to the VPS. Several chats work in the account, and any of them can flip it.
So rule 3 below is not nitpicking: **a product that needs a specific machine must name it
itself.**

**Scopes.** Records are scoped the same way experts and keys are: `search_targets` without
`global` returned 3 records, with `global: true` — 8. So some targets are visible only
within the agent's scope, others across the whole account. **The default is set with
`set_default_target {device_id}`** — per account; in the interface,
`Library → System → Devices → Change default`.

**Rules that follow from this.**

1. **Always pin, and always as an array.** An installed storefront reads a single `target`
   field, sources do not — the canon is `targets: [device_id]` (and `target` as a string
   alongside it, when the message format allows it).
2. **The list is a reservation, not "wherever."** Order matters; put the machine where the
   data lives first, and a fallback second, if the work doesn't depend on the machine.
3. **Don't rely on the default.** It's one per account, changes with a single click, and
   differs across call paths. A product that needs a specific machine must name it itself.
4. **An agent's work cannot be pinned** — if a task must run on a specific machine, an
   expert with `targets` does it, not "an agent that goes there on its own."
5. **`Target … is unavailable` means three different things:** the machine is off; a
   record identifier was passed instead of a device one; the device was deleted. Check
   which kind of identifier it is first — that's free.
6. **A machine from another account answers not with a refusal, but with a syntax error** —
   H104.

**Account hygiene.** Records pile up: the owner had seven records for three live machines,
including a dead one (`11b0c773…`, re-registered on 30 Jul) and someone else's
(`39f81469…`, listener on another account). Dead records aren't harmless: as long as such a
record exists, the platform can pick it for an unpinned call. Cleanup —
`Library → System → Devices`, the "…" menu on the card (appears on hover);
`delete_target` via the API didn't work on every record (letter §49).
