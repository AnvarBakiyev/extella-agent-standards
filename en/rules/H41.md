# H41. A key and its scope: two silent ways to lose a secret

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/rules/INDEX.md).

### H41. A key and its scope: two silent ways to lose a secret

**Findings from the connectors chat, 19 Aug 2026.**

**1. A default-agent substitution writes the key into someone else's scope.** When the
binding to an agent isn't set explicitly, the code substitutes a pre-configured agent,
and the write goes into a scope that isn't the product's own. The key exists, and the
product, working in its own scope, gets a "key not found" refusal — it looks like lost
connections or a platform defect. The binding must be mandatory: either from the
environment, or from a verified local binding. If the scope is unknown, the product
refuses in words and writes nothing.

**2. A fragment of the secret in a record's description comes back through search.** The
interface may show nothing, while a search across the storage returns the record together
with the value. A description must carry only the record's permanent purpose — no key, no
start or end of the value, no fingerprint. This is locked in by a check that forbids even
the first eight characters of the value in the description.

**Related, from the same source.** An extra layer of encryption on top of the platform's
storage turned out to be an unnecessary assumption: the storage already keeps the value
encrypted, and adding your own key file introduced a new failure mode — once that key is
lost, the value can no longer be decrypted. Your own layer can only be removed after
verifying the boundary: the model must have no read or search access to the storage, and
the plaintext value must reach the device alone.
