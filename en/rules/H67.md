# H67. A new subject-matter domain is connected as a CSPL domain, not as new access

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H67. A new subject-matter domain is connected as a CSPL domain, not as new access

When an agent needs to act in someone else's system — a database, mail, files, a
government registry — the temptation is to grant broad access and rely on an
instruction. An instruction is not a boundary: it sits in the prompt, which means it is
negotiable. The boundary is CSPL: the model sends the **name of an operation**, not
code, and the handler decides according to a policy that lives at the client's side and
does not enter the prompt.

Probe on 27 Aug 2026: in the live CSPL-1C, 81% of the code is domain-independent. So
connecting a new domain costs a **registry of operations, adapters, and a default
policy** — the scaffold is taken ready-made (`templates/cspl/`). Two domains built this
way took 128 and 130 lines.

**What a domain must declare.**

Every operation names its effect before execution — `read`, `export`, `draft`, `write`,
`post`, `delete`, or `development` — and the required right. An operation that doesn't
exist yet is declared with a "not implemented" marker: the refusal "this operation isn't
done yet" is understandable to a person, while "unknown operation" looks like breakage.

**What policy, not code, must decide.**

Rights, scope (environments, roots, limits), and which effects require approval. Policy
lives at the client's side, does not enter the prompt, and is not overridden by the
agent's server-side instruction. The model cannot ask itself for a right: it can only
request what is already allowed.

**Anything dangerous goes through approval tied to a fingerprint of the plan.**

The `plan` phase does nothing and returns a fingerprint; the `execute` phase requires
that fingerprint back along with a replay key. The fingerprint is computed over WHAT is
about to be done: the phase, the key, and the approval block itself are not part of it —
otherwise consent taken at the plan stage would never match at execution (caught by a
self-check while building the core; in CSPL-1C this was done correctly from the start).

**A product-level ban is set with two locks.**

The right is turned off in permissions, and the effect is separately marked forbidden.
Then granting the right by mistake does not open the action. This is how sending mail is
built: the canon "a person sends it" stops being a wish and becomes a mechanism.

**Verified by the domain's own self-check**, which must be able to fail: what's allowed
goes through, and going out of scope, an unknown operation, an extra input field, a
policy ban, and swapping in someone else's approval fingerprint are all rejected.
