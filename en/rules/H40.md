# H40. An expert's response has a ceiling around 200 KB, and it isn't named an error

Full corpus — `DEPLOY_REQUIREMENTS.md`; rule index — [rules/INDEX.md](https://raw.githubusercontent.com/AnvarBakiyev/extella-agent-standards/main/en/rules/INDEX.md).

### H40. An expert's response has a ceiling around 200 KB, and it isn't named an error

**Probed by the connectors chat, 18 Aug 2026.** Small responses go through fine, a full
directory snapshot returns 200 with no usable result, and parsing already fails on the
page's side. The threshold in practice is around 200 kilobytes.

**Workaround.** A response above the threshold is compressed, encoded, and marked with a
separate field; the shell recognizes the marker and decompresses it with the browser's
own tools inside the shared wrapper-parsing loop. If an old window lacks this capability,
it must tell the person "update Extella" in words, not show a blank screen.

**The same class of bug at a different layer, probed on 18 Aug 2026 (embedded product
chat).** A large database's schema didn't fit within the previous limit on a field
description, and an otherwise correct read came back with code 500. To the person, this
looked like "the source isn't responding," though the actual issue was size. The limits
were raised to 64 kilobytes for a composite description and 256 kilobytes for the whole
envelope, and exceeding them now returns a precise code, rather than a raw exception's
text or a false five-hundred. General rule: a size limit must name itself, otherwise it
gets mistaken for the source being broken.

**Related, from the same probe.** A live call confirmed several nested wrappers, some of
them strings with markup inside. The platform doesn't promise their exact number, so the
rule is phrased as a safety limit, not as a measurement: **parse to a bounded depth, at
least down to ten.** Ten is the limit of the protective loop, not a measured count; this
must not be confused, or the next reader will conclude the platform guarantees ten.

The transport parser must be kept separate from parsing the domain response: a domain
object can also have a `result` field, and a shared loop will eat the data along with the
wrapper. Strip the wrapper only on a provable transport marker; the mere presence of a
`result` field is not such a marker. The fix was made right here: parsing on the guide's
page was raised from four levels to ten and stops as soon as it sees a domain response.
Verified against seven wrappers and against a domain object with its own `result` field.
