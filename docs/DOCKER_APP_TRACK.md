# Docker-трек: серверное приложение → контейнер → окно ОС

Проложен 20.08.2026 на Uptime Kuma («Сторож»). Всё ниже — замеры, не мнения.
Исполняемый источник — `tools/install_docker_app.py` и `tools/cabinet_server.py`
(прокси-режим); при расхождении текста и кода прав код.

## Зачем трек

Добыча спроса 19.08.2026: по звёздной массе ≈65% желанных приложений — серверный
docker-класс (Immich 112k⭐, n8n 201k, Vaultwarden 66k, Stirling-PDF 90k, Jellyfin 56k),
браузерная статика — ≈6%. Браузерный конвейер ловит хвост спроса, этот трек — голову.

## Как поставить приложение

    python3 tools/install_docker_app.py \
        --образ louislam/uptime-kuma:1 --slug uptime-kuma --имя "Сторож" \
        --порт-внутри 3001 --том /app/data \
        --лицензия https://raw.githubusercontent.com/louislam/uptime-kuma/master/LICENSE \
        --глиф activity

Шаги установщика: докер жив → compose и контейнер (на внутреннем порту) →
прокси с шимом наружу → проба перезапуском → лицензия → плитка Bronze
Engraved, карточка, окно. Дальше руками: заполнить listing.json, выложить
предрелизом, Publish — владелец. Предрелиз — это версия продукта, которую видит
только автор.

## Правила трека — каждое закреплено самопроверкой

- **Порт только 127.0.0.1.** Контейнер на 0.0.0.0 раздаёт приложение всем
  соседям по сети — у чужого ноутбука в том же кафе появляется ваш сторож.
- **Данные — томом в `~/extella-cabinet/docker/<slug>/данные`**: видны файлами,
  бэкапятся, переживают пересоздание контейнера.
- **Перезапуск — шаг установки, а не обещание.** Контейнер перезапускается и
  обязан ответить снова, иначе установка не состоялась.
- **`restart: unless-stopped`** — переживает ребут вместе с Docker Desktop;
  LaunchAgent контейнеру не нужен (прокси — нужен, его ставит установщик).
  Docker Desktop должен стартовать при входе — проверить галку в его настройках.
- **Первичный пароль задаёт владелец.** Агент не заводит аккаунты и не выбирает
  пароли даже в локальном контейнере.
- **Беспарольный локальный контур — по слову владельца** (решение Анвара
  21.08.2026: «вход уже охраняет Extella»). Два штатных пути: выключить auth
  самого приложения (Kuma: setting `disableAuth`) или автовход прокси —
  `cabinet_server --автовход <json {путь, тело}>`: при 401 прокси входит сам
  машинным секретом (файл 600 рядом с .env, человеку не показывается) и
  повторяет запрос; сессию держит банка кук. Порт при этом ТОЛЬКО 127.0.0.1 —
  беспарольность не выходит за пределы компьютера.
- **Вход бывает не кукой.** Замеры 21.08.2026 на Memos: (1) токен приезжает
  ПОЛЕМ ТЕЛА ответа (`accessToken`), а не Set-Cookie — конфиг `"кука_из_тела":
  {"поле": "accessToken", "как": "bearer"}` кладёт его в банку спец-ключом, и
  прокси шлёт `Authorization: Bearer` (кука с тем же токеном даёт 401, Bearer —
  200); (2) refresh-куку приложение ставит служебным заголовком
  **`Grpc-Metadata-Set-Cookie`** (обычный путь connect-rpc) — сборщик по имени
  «Set-Cookie» её не видит, и окно показывает форму логина при живом токене.
  Прокси собирает оба заголовка и на входе, и на каждом проксируемом ответе:
  без второго сессия ломается в середине работы при ротации токена.

## Песочница окна ОС: полный список дверей (кровью)

Окно ОС — песочница без адреса (`Origin: null`). Для докер-класса страницы
отдаёт контейнер, в файлы шим не вставить — поэтому **наружу смотрит прокси**,
который вшивает шим на лету. Всё, что убивало окно, по порядку обнаружения:

| Дверь | Как выглядит | Лечение |
|---|---|---|
| localStorage / sessionStorage | молча теряет работу | шим: хранилище → файл на диске |
| document.cookie | бросает SecurityError | шим: cookie-банка в памяти |
| IndexedDB | «вежливый отказ» вешал localforage вечным Loading | шим: `indexedDB = undefined` — «баз нет», это умеют все. Побочный шум: сборки, зовущие `indexedDB.open` без проверки, бросают TypeError «reading 'open'» — докладчик шима не считает это сбоем (замер 20.08.2026, Доска работала, полоска её хоронила) |
| **History API** | `replaceState` бросает; роутер SPA умирает в цикле — белое окно | шим: пробуем родной, отказ глотаем |
| **X-Frame-Options** | контейнер шлёт SAMEORIGIN; браузер скачивает документ и МОЛЧА не рисует его во вложении — белое окно без ошибок и без запросов за скриптами | прокси снимает XFO (и CSP) |
| **Шестая: Cross-Origin-* + сетевые куки** (21.08.2026, tududi/helmet) | `Cross-Origin-Resource-Policy: same-origin` душит В ПЕСОЧНИЦЕ каждый скрипт и fetch (происхождение окна — null, всё «кросс»): в обычной вкладке приложение живо, в окне ОС — белое. Плюс песочница режет сетевые куки — сессия логина не живёт. И дубль ACAO ломает CORS целиком | прокси снимает семейство Cross-Origin-* и Set-Cookie (куки держит банка прокси в памяти, доклеивает в запросы), предполёт проксируемых путей отвечает сам; ACAO шлёт ТОЛЬКО end_headers — один раз |
| **Одиннадцатая: рабочие потоки (Worker)** (21.08.2026, Stirling-PDF) | документ добавлен, просмотрщик вечно «Loading tool…»; в консоли — `Refused to cross-origin redirects of the top-level worker script` | у окна происхождение отобрано (null), поэтому ЛЮБОЙ обычный адрес для него чужой, а главный скрипт воркера с чужого адреса браузер грузить отказывается. Библиотеки (pdf.js) пробуют обойти своей blob-обёрткой, но тянут внутри неё тот же чужой адрес. Шим забирает код воркера сам (обычным запросом) и отдаёт его воркеру внутри blob — снаружи грузить нечего. Перехват стоит ПЕРВЫМ в шиме: поставленный позже, он не успевает — приложение забирает родной конструктор раньше |
| **Девятая: Web Locks** (21.08.2026, Stirling-PDF) | приложение открылось, но инструмент вечно «Loading tool…»; в консоли `Failed to execute 'request' on 'LockManager': Access to the Locks API is denied` | шим отдаёт замок сам (делить в одном окне нечего). **Ловушка, стоившая круга правок:** проверять НАЛИЧИЕ `navigator.locks` бесполезно — объект на месте, бросает только ВЫЗОВ. Подмена под условием «если нет» не встаёт вовсе; ставить всегда, а родные замки пробовать внутри |
| **Десятая: базы браузера, третий подход** (21.08.2026) | Stirling держит В БАЗАХ сами файлы: на «баз нет» его менеджер не уходит в запасной путь, а вечно крутит спиннер «My Files» — документ не открыть | пройдены три состояния: «вежливый отказ» событием (повесил Таблицу через localforage, 19.08) → `indexedDB = undefined` (спасло Доску и Таблицу, повесило Stirling) → **маленькая настоящая база в памяти окна** (открытие, хранилища, ключи, индексы перебором, курсоры). Операции честно завершаются, приложение видит пустое хранилище. Плата названа в полоске и в карточке: эти базы живут до закрытия окна |
| **Восьмая: окно на голом «/»** (21.08.2026, Заметки/memos + PDF/Stirling) | приложение внутри загружается и работает (журнал прокси: все ответы 200), но человек видит только логотип Extella — и после перезапуска тоже. В журнале ОС: `[overlay] ready → boot` без обратного перехода | это не песочница, а оболочка ОС: `updateOverlayForNavigation` считает маршрут `/` «незавершённым переходом роутера» и держит шторку до появления настоящего маршрута. Приложения, которые сами уходят с корня, спасаются (tududi → `/today`); те, чья главная И ЕСТЬ корень, — нет. Лечение на нашей стороне: открывать окно на явном маршруте (`--путь /explore`, `--путь /home`). Инструмент предупреждает, если путь остался «/» |
| **Седьмая: navigator.serviceWorker** (21.08.2026, tududi) | само ЧТЕНИЕ свойства бросает SecurityError — загрузчик умирает до дела; настоящая причина видна только после crossorigin-пометки скриптов прокси (иначе пустое «Script error.») | шим удаляет свойство («воркеров нет»), не даёт браузер — тихая заглушка |

**«Открыть отдельным окном» в Электроне — легенда**: новое окно наследует ту же
песочницу. Запасного пути нет, есть только починенное основное.

## Прокси-режим cabinet_server

    python3 cabinet_server.py --папка <любая> --порт 34788 --имя <slug> \
        --данные ~/extella-cabinet/данные --прокси-на 44788 \
        --шим ~/extella-cabinet/storage_shim.html

Всё, кроме служебных путей (`/_extella_storage|_version|_action`), проксируется
на внутренний порт; в `text/html` вшивается шим. Снимаются: CSP (зарезал бы наш
встроенный скрипт), X-Frame-Options (см. таблицу), сжатие (шим в gzip не
вставить). Сокеты (socket.io) живут длинным опросом через прокси — WebSocket
наш сервер не умеет, и это оказалось не нужно.

## Как диагностировать белое окно (метод трёх раундов)

0. **Сначала спросить: а грузится ли приложение вообще?** `--журнал` у прокси
   (`cabinet_server --журнал`) печатает каждый запрос. Если ответы 200 идут, а
   человек видит логотип — виновата не песочница, а шторка ОС (восьмая дверь).
1. **Журнал охоты**: включить лог запросов на прокси, попросить владельца
   обновить окно один раз. Запросов нет — не доходит; HTML есть, ассетов нет —
   документ не рендерится (ищите XFO/CSP); всё есть — умирает скрипт.
2. **Репродуктор**: страница приложения + замки песочницы (бросающие
   localStorage/cookie/IDB/History) открывается там, где видна консоль.
   Помнить: XFO в репродукторе НЕ виден — он бьёт только вложение.
3. Чинить только по факту из консоли или журнала. Три двери из пяти были
   найдены именно так; ни одна догадка «по памяти» не подтвердилась.


## Хранилище окна: два правила, оплаченные кровью

**Писать на диск С ЗАДЕРЖКОЙ (400 мс).** Приложения проверяют хранилище на
живость так: пишут ключ со случайным именем, читают, тут же удаляют. Stirling
делал это десятками — в файле работы осело 20 ключей `lswt-…` из 27. Каждая
проба уходила отдельной записью и поднимала счётчик версии, а счётчик versions —
это сигнал «работу поменял кто-то другой»: окно предлагало «Обновить», а при
простое перечитывало себя само. Владелец видел приложение, которое
самопроизвольно моргает. Задержка схлопывает пару «записал-удалил» в одну
запись: на диск едет итог, мусор до него не доезжает. Недописанное досылается
на `pagehide` (sendBeacon).

**Приложение возвращается на корень САМО — и это главная часть беды.**
Открыть окно на маршруте мало, увести корень на прокси — тоже мало: роутер
приложения через полсекунды переводит адрес на «/» своим pushState, без
единого запроса в сеть (замер 21.08.2026, Заметки: `/home` → `/` за 500 мс,
шторка падала при каждом нажатии плитки). Держит адрес шим: попытку встать на
корень он подменяет стартовым маршрутом окна, а ссылкам «домой» правит цель.
Проверка без окна ОС: открыть приложение в браузере и посмотреть
`location.pathname` несколько секунд подряд — он обязан остаться на маршруте.

**Голого «/» у приложения не должно существовать.** Мало открыть окно на
`/home`: внутри приложения есть своя кнопка «домой», она ведёт на `/`, и шторка
ОС падает снова — посреди работы (замер 21.08.2026, Заметки). Поэтому увод
делает прокси: `--корень-на /home` переводит навигацию человека с корня на
настоящий маршрут, а запросы данных не трогает.

**Вечный поток событий не даёт странице догрузиться.** Окно ОС снимает шторку
по событию «страница загружена»; открытый SSE его откладывает. Либо поток
переливать (прокси умеет), либо гасить: `--глушить /api/v1/sse`. Проверка без
окна ОС: `document.readyState` и `loadEventEnd` в браузере — у здоровой
страницы load наступает за сотни миллисекунд.

**Счётчик версии — не то же самое, что «изменение работы».** Прежде чем считать
правку чужой, спроси: не сам ли я её только что сделал (счётчик «в полёте») и
есть ли в ней смысл для человека.

## Чужое приложение не умеет — доделываем внутри него, а не рядом

Встроенный просмотр PDF в окне не запускался: движок живёт в рабочем потоке,
а потоки в песочнице мертвы. Соблазн — поставить второе приложение для чтения.
Слово владельца: «зачем мне два инструмента». Правильный ответ — доделать
внутри того же окна.

Как сделано (шим, «спасательный просмотр»): если область просмотра висит
дольше нескольких секунд, шим берёт документ ИЗ ХРАНИЛИЩА САМОГО ПРИЛОЖЕНИЯ
(наша база-заглушка — он уже там, человек его открыл) и показывает своим
слоем поверх: страницы, листание, увеличение, закрытие. Библиотека кладётся
рядом с приложением (`/_extella_page/lib/`), считает в главном потоке.

Замер 22.08.2026: документ найден в `stirling-pdf-files`, показан «1 / 27»,
страница отрисована. Пользователь остаётся в одном приложении.

**Библиотеку брать У САМОГО ПРИЛОЖЕНИЯ, а не свою.** Своя копия другой версии
спорит с уже загруженной за общий реестр и падает «The API version … does not
match the Worker version …». Коварство в том, что в браузере это проходит, а в
окне — нет: там приложение успевает загрузить свою первым. Ищем её среди
подключённых скриптов (`script[src*="/assets/"]`), своя копия остаётся
запасным путём.

**Удаление продукта из витрины** (пригодилось сразу: отдельное приложение для
чтения оказалось лишним, владелец велел убрать целиком): HTTP-метод DELETE на
`/api/listing/<id>` и заголовок `X-Extella-Token` — с обычным `X-Auth-Token`
приходит 401, а «пути с delete» (`/api/delete-listing/…`) отвечают 404 и уводят
в сторону. Ответ `{"status":"success"}`. Плитку со стола снимать отдельно:
листинг и плитка — разные слои.

**Проверять такое можно без окна ОС:** флаг `#extella_no_workers` включает
песочный режим целиком — мёртвые потоки, база-заглушка, спасательный просмотр.
Флаг брать ИЗ ХЭША: параметры адреса приложение теряет при своей навигации.

## Потолок памяти и долгая работа: два молчаливых убийцы

**Потолок памяти душит тяжёлые операции.** Ставить `mem_limit` правильно, но
число берётся не из головы: у Stirling 2 ГБ хватает на открытие и обычные
операции, а распознавание текста упиралось в потолок — JVM выходила по
нехватке памяти, контейнер перезапускался, и снаружи это выглядело как
«приложение молчит» (замер 22.08.2026). На 4 ГБ OCR прошёл: 27 страниц
по-русски за 42 с. **Проверять потолок самой тяжёлой операцией, а не запуском.**

**Долгую работу нельзя рвать по таймауту прокси.** Полторы минуты — мало:
приложения делают многоминутную работу одним запросом. Прокси ждёт 30 минут.

**Языки распознавания в образ не входят.** У Stirling их шесть, русского и
казахского нет: запрос отвечает «none of the selected languages are valid».
Файлы языков кладутся томом в `tessdata` и переживают пересоздание контейнера.

## Контейнер смотрит на мир из своей норы

У контейнера СВОЙ 127.0.0.1 — это он сам, а не Мак. Монитор локальной службы
по адресу `http://127.0.0.1:34786` отвечает «ECONNREFUSED» (замер 20.08.2026,
первый же монитор владельца). Дорога из контейнера к службам Мака — имя
`host.docker.internal`: проверено изнутри контейнера, службы на 127.0.0.1 Мака
по нему отвечают. Внешние адреса (https://…) работают как обычно.

## Приёмка

Установка состоялась, когда: контейнер отвечает после перезапуска · данные
лежат файлами в томе · порт не торчит наружу · плитка и карточка на витрине ·
**владелец видит интерфейс во вложенном окне ОС и проходит первичную настройку
сам**. Сторож прошёл всё 20.08.2026.
