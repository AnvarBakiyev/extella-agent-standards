# Канон установщика одной кнопкой

**Канонический дом документа — этот репозиторий** (`extella-agent-standards`).

Проверено вживую 15–20.08.2026 на трёх продуктах: мост Codex, мост Claude Code и
локальная модель (LM Studio). Каждый ставится одной кнопкой на странице продукта
и проходит путь **страница → устройство пользователя → рабочее состояние** без
единого запроса к платной модели во время установки.

Каждый пункт ниже написан по факту: рядом сказано, чем он проверен и что
ломается без него. Почти каждый куплен настоящей поломкой на машине тестера —
поэтому опровергнутые варианты оставлены намеренно, они дороже подтверждённых.

---

## Слова, которые дальше встречаются постоянно

**Скоуп** — это набор объектов, доступных конкретному агенту; у каждого агента
он свой. **Листинг** — это карточка продукта в магазине. **Гейт** — это
автоматическая проверка, которая не пускает выкладку, пока условие не выполнено.
**Предрелиз** — это версия продукта, которую видит только автор.

**Установщик** здесь — это Expert (серверная функция агента), который выполняет
установку по шагам. Он исполняется на устройстве пользователя, где стоит
приложение Extella, и на каждый вызов возвращает строку JSON.

---

## 1. Шесть безмодельных шагов, каждый со своим именем

Установка разбита на короткие шаги, у каждого своё имя действия: `preflight`,
`install`, `credentials`/`model`, `bridge`/`server`, `configure`, `verify`. Плюс
отдельный `status` — перечитка состояния.

Правила, общие для всех шагов:

- **Ни один шаг не запускает платную модель.** Каждый ответ несёт поля
  `model_called: false`, `agent_called: false`, `paid: false`. Страница считает
  ответ успешным, только если все три равны `false`. Так проверено, что кнопка
  не тратит план пользователя во время установки.
- **Шаги идемпотентны.** Повторный вызов уже выполненного шага не ломает
  установку, а подтверждает её. Отсюда стратегия восстановления: при сбое или
  паузе достаточно нажать кнопку снова, установка продолжится с недостающего
  шага.
- **`status` не входит в список «выполненных» шагов.** Он не делается и не
  остаётся сделанным — это перечитка остальных плюс живая проверка здоровья.
  Ранняя версия сообщала `verify: false` сразу после того, как проверка вернула
  «готово», — статус противоречил факту.

## 2. Версия установщика едет в каждом ответе

Каждый ответ содержит поле `setup_version`. Без него нельзя отличить «исправление
не помогло» от «отвечает старая версия».

Замер-урок 18.08.2026: у тестера на экране была версия 3.2.4, а в терминал он
вставил вывод, снятый до неё; разбор ушёл на круг переписки, прежде чем стало
видно, что версии разные. С тех пор версия видна в каждом ответе и в тексте
каждого отказа.

## 3. Отказ называет следующий шаг, а не только проблему

Сообщение об отказе, из которого нельзя понять следующее действие, — это дефект,
даже когда код формально прав.

Пары «было — стало» из живых разборов:

| Было | Стало |
|---|---|
| «Не удалось проверить вход в Claude Code.» | «Войдите в Claude Code: выполните `claude auth login`, затем повторите.» |
| «Текущий аккаунт Extella недоступен.» | «Откройте приложение Extella на этом компьютере и войдите — токен появится сам; создавать файл вручную не нужно.» |
| «Claude Code не установлен.» | «Claude Code не найден. Искали в: `…каталоги…`. Если он лежит не там, пришлите вывод команды `which claude`.» |

Отказ по железу называет оба числа: «памяти достаточно (32 ГБ), но на диске
свободно 1 ГБ, а модели нужно 22» — а не общее «не хватает места».

## 4. Токен читается из четырёх источников по порядку

Установщику нужен токен доступа к аккаунту Extella. Пользователь его не вводит и
не создаёт файл руками. Порядок чтения (канон `store_app/update.py`):

1. **окружение процесса** — `os.environ["EXTELLA_API_TOKEN"]`. Приложение кладёт
   токен в окружение исполняемого Expert; это штатный источник.
2. **файл** `~/.extella/api_token.txt` — приложение пишет его само при входе.
3. **`launchctl getenv EXTELLA_API_TOKEN`** — если токен уже выставлен прежней
   установкой.
4. **конфиг приложения** `~/extella_wizard/app/config.json`, поле `auth_token`.

Замер-урок 18.08.2026 на машине тестера: первые три источника пусты, при этом
Expert исполняется — значит приложение авторизовано, и токен лежал ровно в
четвёртом. Реализованы были только первые три; отсюда правило: раз Expert
работает, один из этих источников обязан содержать токен, и читать надо все.

**Из конфига берётся только токен, а не идентификатор агента.** В конфиге может
стоять другой агент, и чужой идентификатор даёт «ключа нет» на существующем
ключе.

Отдельно: инжекция токена в окружение **непостоянна между машинами** — на одной
приложение кладёт его, на другой нет. Это разница в версии приложения, поэтому
полагаться на один источник нельзя.

## 5. Гейт по железу И по диску до долгой загрузки

Проверять только память недостаточно.

Замер-урок 19.08.2026: загрузка модели 22 ГБ оборвалась на восьмом гигабайте,
потому что на диске оставался 1 ГБ, а `preflight` смотрел лишь на память. Теперь
модель выбирается по памяти и по свободному месту с запасом, а отказ называет оба
числа. Лестница моделей (сильная → средняя → отказ) выбирает верхнюю, что
проходит по железу.

## 6. Долгий шаг идёт в фоне и опрашивается, а не ждётся

Платформа откладывает вызов, который длится дольше примерно 51 секунды: вместо
результата приходит ссылка на фоновую задачу, дождаться которую страница не
может (замер probe-Expert со сном 18.08.2026; поле `timeout` в теле запроса
платформа принимает и игнорирует, а пути ожидания задачи для токена страницы не
существует).

Поэтому единственный долгий шаг — загрузка модели — устроен так:

- шаг запускает загрузку в отдельном процессе и **сразу возвращается** с полем
  `finished: false` и прогрессом;
- страница опрашивает шаг раз в 20 секунд и рисует прогресс;
- завершение определяет установщик (`finished: true`), а не страница.

Признак «модель на диске» читается запуском `lms ls`: частично скачанные файлы в
списке не появляются, поэтому чтение честное.

## 7. Предохранитель против бесконечного перезапуска

Умершая загрузка — не повод крутить вечный цикл. Счётчик попыток на каждый
профиль: две смерти подряд дают честную ошибку с хвостом журнала, а не молчаливый
перезапуск. Файлы состояния загрузки разведены по профилю, чтобы прогресс одного
не показывался за другой.

## 8. Внешнюю программу надо и найти, и суметь запустить

Приложение стартует из окна, а не из терминала, и наследует короткий `PATH`.
Поэтому поиск программы по `PATH` почти всегда промахивается.

Замер-урок 17–18.08.2026 на двух машинах:

- программа (`claude`, `codex`) стояла в каталоге менеджера версий Node —
  `~/.nvm/versions/node/<версия>/bin`, которого в коротком `PATH` нет;
- чтение `PATH` из логин-оболочки не помогло: `zsh -l` читает `.zprofile`, но не
  `.zshrc`, а менеджер версий настраивается именно в `.zshrc`.

Рабочий поиск: жёсткий список каталогов **плюс** прямой перебор каталогов
менеджеров версий (nvm, fnm, n, volta) **плюс** `PATH` из интерактивной
логин-оболочки (`zsh -ilc`).

И этого мало: найти программу — половина дела. `claude` из менеджера версий —
это скрипт, которому рядом нужен `node`. Каталоги поиска обязаны попасть в `PATH`
**при запуске** программы, иначе она падает с «node не найден» там, где сама
найдена.

## 9. Читай статус в ответе, а не код возврата

Замер-урок 18.08.2026: `claude auth status --json` у невошедшего пользователя
печатает корректный JSON `{"loggedIn": false}` и завершается **с кодом 1**.
Проверка кода возврата превращала самое обычное состояние — «вход не выполнен» —
в «не удалось проверить вход». Сначала читается вывод; код возврата смотрится,
только если вывод неразборчив.

## 10. Метка версии в коде обязана совпадать с версией листинга

Замер-урок 18.08.2026: замена строки версии без проверки её наличия молча не
срабатывала, и ответы установщика три версии подряд называли устаревший номер.
Теперь выкладка сверяет метку `SETUP_VERSION` в каждом Expert с версией листинга
и отказывается публиковать при расхождении.

## 11. Запись Expert привязана к скоупу последнего сохранения

`save_expert(global=true)` не создаёт запись, общую для всех скоупов. Чтение
именем работает отовсюду, а исполнение — только из скоупа, сохранившего запись
последним; из остальных приходит «Expert not found». Воспроизведение — семь
шагов между двумя скоупами (см. `plugins/.../DEFECTS.md`).

Следствие для установщика: раздавать один Expert всем агентам через один
`global:true` нельзя. Рабочий обход — записать отдельную копию `global:false` в
каждый изменяемый скоуп и проверить каждую **запуском**, а не чтением: запись
читается верной и при этом не запускается (замер на одном скоупе из 38). Раздача
идёт порциями, потому что полный проход по десяткам агентов уходит в отложенную
задачу (см. пункт 6).

## 12. Шлюз страницы видит только Expert из установленной версии

Замер-урок 19.08.2026: новый Expert через `/api/app-agent/run` отвечает **502**,
хотя через прямой вызов ядра работает. Любое имя вне снимка установленной версии
даёт 502, а не 404. Значит кнопка со страницы заработает только после обновления
установленного приложения до версии, где Expert появился.

## 13. Запись конфигурации — атомарная и с резервной копией

Переключение конфига приложения (например, на локальную модель) пишется во
временный файл и переставляется на место одним `os.replace`, а прежний конфиг
сохраняется рядом с отметкой времени. Так частичная запись не оставляет
приложение с испорченным конфигом.

## 14. Общий код — один источник, копии пересобираются

Установщики нескольких продуктов делят общий код (поиск программы, чтение токена,
установка службы). Общий код живёт в одном каноническом месте, а копии в
продуктах **пересобираются** из канона, а не правятся на месте. Гейты
`check_onboarding_copies` и `check_platform_client_copies` не пускают выкладку,
пока копия отстаёт от канона. Порядок при расхождении: сначала обновить канон,
потом пересобрать копии.

## Контракт страницы продукта

Страница исполняется в рамке приложения на локальном адресе. Что она умеет
передать установщику — это поверхность атаки, поэтому:

- **Белый список полей, а не копирование.** В установщик проходят только `action`
  и заранее названные поля (номер порции, профиль из двух допустимых значений).
  Числа приводятся к числу, значения-перечисления сверяются с точными литералами.
- **Поля `timeout` в запросе нет** — платформа его игнорирует (пункт 6). Ставить
  его — давать ложное обещание.
- **Отложенная задача распознаётся до разбора результата** и называется своими
  словами: «этап продолжается в фоне, подождите и нажмите снова».
- **Прогресс виден по шагам** с именем шага, а не застывшим «Подключаю…».

Внутри рамки приложения установку может вести приёмник host-модуля, а страница
рисует шаги по событиям прогресса. У событий нет повтора после перезагрузки
рамки, поэтому итог восстанавливается перечиткой `status`, а не ожиданием
сообщения.

## Что этот канон даёт следующему продукту

Каждый пункт выше был поломкой на живой машине. Следующий установщик, собранный
по этому канону, получает их решёнными до первого запуска у пользователя: он
находит программу там, где она есть; читает токен из того источника, что заполнен
на этой машине; не тратит план во время установки; переживает медленную загрузку
и потерю сети; называет пользователю следующий шаг вместо тупика; и не расходится
с общим кодом незаметно.
